Runpod CLI is an [open source](https://github.com/runpod/runpodctl) command-line tool for managing your Runpod resources from your local machine. You can manage Pods, Serverless endpoints, templates, network volumes, and models, transfer files between your system and Runpod, diagnose issues, and view account information.

## Quick start

After installing and configuring `runpodctl`, you can start managing resources immediately:

```bash
runpodctl doctor                    # First time setup (API key + SSH)
runpodctl gpu list                  # See available GPUs
runpodctl template search pytorch   # Find a template
runpodctl pod create --template-id runpod-torch-v21 --gpu-id "NVIDIA RTX 4090"
runpodctl pod list                  # List your Pods
```

## Install Runpod CLI locally

Every <PodTooltip /> you deploy comes preinstalled with `runpodctl` and a Pod-scoped API key. You can also install it on your local machine to manage resources remotely.

### Step 1: Choose an installation method

Choose the installation method that matches your operating system.

<Tabs>
<Tab title="Install script">

The install script automatically detects your operating system and architecture:

```bash
curl -fsSL https://cli.runpod.net | sudo bash
```

The script runs as root and installs the latest version to `/usr/local/bin`. For installation without root access, use the non-root instructions in the Linux tab.

<Note>
The install script verifies the downloaded release against its SHA-256 checksum before installing, so it needs a checksum tool to be present: `sha256sum` on Linux or `shasum` on macOS. These are preinstalled in most environments, but on minimal images without one the install aborts.
</Note>

### Step 2: Configure your API key

Before you can use `runpodctl` locally, you must configure it with an [API key](/get-started/credentials).

The easiest way to set up your API key and SSH configuration is with the `doctor` command:

```bash
runpodctl doctor
```

This command guides you through first-time setup, including API key configuration and SSH key setup.

Alternatively, you can manually configure your API key:

```bash
runpodctl config --apiKey YOUR_API_KEY
```

After running the command, you should see a confirmation message similar to this:
```text
saved apiKey into config file: /Users/runpod/.runpod/config.toml
```

### Step 3: Verify installation

To verify that `runpodctl` installed successfully, run this command:

```bash
runpodctl version
```

You should see which version is installed:

```bash
runpodctl v2.0
```

## Command groups

Runpod CLI organizes commands into groups based on the resource type:

| Command | Alias | Description |
|---------|-------|-------------|
| `runpodctl pod` | | Manage Pods (create, list, start, stop, delete) |
| `runpodctl serverless` | `sls` | Manage Serverless endpoints |
| `runpodctl template` | `tpl` | List, search, and manage templates |
| `runpodctl model` | | Manage models in the model repository (add, list, remove) |
| `runpodctl hub` | | Browse and deploy from the Runpod Hub |
| `runpodctl network-volume` | `nv` | Manage network volumes |
| `runpodctl registry` | `reg` | Manage container registry authentications |
| `runpodctl gpu` | | List available GPUs |
| `runpodctl datacenter` | `dc` | List datacenters |
| `runpodctl billing` | | View billing history |
| `runpodctl user` | `me` | View account information |
| `runpodctl ssh` | | Manage SSH keys and get connection info |

## Output format

Modern resource commands write successful output to standard output as JSON by default, which makes runpodctl scriptable and agent-friendly. Use the `--output` flag to switch to YAML:

```bash
runpodctl pod list                    # JSON (default)
runpodctl pod list --output=yaml      # YAML
```

The supported formats are `json` and `yaml`. For commands that reach normal pre-run validation, an unsupported `--output` value fails with a `usage_error`. Help paths do not validate this flag.

The legacy resource verbs listed below retain their historical table or plaintext success output.

`template search` and `hub search` emit `[]` on standard output when nothing matches, instead of a prose message, so a caller piping the output into a JSON parser gets a valid empty list on the no-match case.

### Error format

Except for the legacy commands listed below, runpodctl reports failures as a single flat JSON object on standard error and exits with a non-zero status. Branch on the `code` field, never on the message text.

Standard error can also contain plaintext. `pod create --wait` and `serverless create --wait` print wait progress before the JSON error, `serverless update` can print a partial-update warning before it, and `receive` can print `connecting...` immediately before it without a newline. Do not decode the entire standard error stream as one JSON document; extract the JSON error object even when it is adjacent to plaintext, and decode it separately so you retain fields such as `id` when a wait fails.

The JSON error object has this shape:

```json
{"error":"failed to get endpoint: endpoint not found","code":"not_found","status":404}
```

| Field | Description |
| --- | --- |
| `error` | Human-readable message, unwrapped rather than a nested JSON blob. |
| `code` | Stable, lowercase identifier for the failure class. Present on every error emitted through the central error handler. |
| `status` | HTTP status when an API error provides one. GraphQL errors returned inside an HTTP `200` response usually omit this field, so branch on `code` rather than `status`. |
| `id` | ID of a resource that exists despite the failure, when available. For example, a failed `create --wait` can leave a billable resource behind. |

Codes runpodctl generates:

| Code | Meaning |
| --- | --- |
| `usage_error` | The invocation is invalid. Cobra flag parsing and Cobra argument validation errors also print usage after the JSON object. |
| `not_found` | The resource was not found. During `--wait`, it may have been deleted or never became visible; check for an `id` before assuming nothing was created. |
| `bad_request`, `unauthorized`, `forbidden`, `rate_limited`, `server_error`, `api_error` | Derived from the HTTP status returned by the API when it does not provide an explicit code. |
| `conflict` | The resource state prevents the operation. This can come from an HTTP `409` response or a locally detected terminal state during a wait. |
| `graphql_error` | GraphQL returned an error, either in an HTTP `200` response body or as a non-`200` response. |
| `no_credentials` | No Runpod API key, or no required network-volume S3 credentials, is configured. For an API key, run `runpodctl doctor` or set `RUNPOD_API_KEY`. For network-volume transfers, set `RUNPOD_S3_ACCESS_KEY` and `RUNPOD_S3_SECRET_KEY`, pass `--s3-access-key` and `--s3-secret-key`, or set `s3AccessKey` and `s3SecretKey` in `~/.runpod/config.toml`. |
| `network_error` | The API could not be reached because of a transport failure such as DNS, connection refusal, TLS, or a network timeout. |
| `create_uncertain` | A Pod create may have succeeded, but its outcome is unknown. Check `runpodctl pod list` before retrying to avoid creating a duplicate Pod. |
| `dependent_endpoints` | A model cannot be removed because endpoints still reference it. Detach or replace the model references first. |
| `timeout` | An invoke request, a log-stream response wait, or a job or model wait timed out. Control-plane request timeouts use `network_error` instead. Read the error message before retrying because work may still be running. |
| `job_failed` | A Serverless job reached a terminal state other than `COMPLETED`. The job payload is still written to standard output. |
| `wait_timeout`, `wait_interrupted` | A `create --wait` operation timed out or was interrupted. The created resource still exists, and its ID is included in `id` when available. |
| `transfer_incomplete` | A network-volume transfer stopped partway. Rerun the transfer to resume it. |
| `volume_full` | A network-volume upload reached the volume's size limit. Expand the volume, then rerun the transfer. |
| `cli_error` | Any other local failure, such as validation, configuration, bad input, or a malformed `RUNPOD_API_URL`. |

The API can also return its own code, which is passed through in lowercase. Treat the list above as the set the CLI generates rather than an exhaustive one.

### Exit codes

Documented resource and utility commands exit non-zero on failure, including `model`, `update`, `send`, and `receive`. Do not rely on stdout being empty to detect failure. Check the exit code and parse the extracted JSON error object.

A few legacy surfaces do not use the JSON error handler:

- Runtime failures inside the legacy pod verbs (`get pod`, `create pod`, `remove pod`, `start pod`, `stop pod`, `create pods`, `remove pods`) and `get cloud` print `Error: <message>` via Cobra and exit `1`. Cobra flag parsing and Cobra argument validation still use the structured `usage_error` path, but validation inside a legacy handler, such as `runpodctl get cloud abc`, prints plaintext.
- The removed `project` command prints SDK migration guidance to standard error and exits `1`.

Parsers should tolerate non-JSON error output from those commands.

### API environment variables

| Variable | Default | Description |
| --- | --- | --- |
| `RUNPOD_API_KEY` | — | API key. Also settable via `runpodctl doctor` or `~/.runpod/config.toml`. |
| `RUNPOD_API_URL` | `https://api.runpod.io/v2` | REST control plane (config key `restApiUrl`). |
| `RUNPOD_GRAPHQL_URL` | `https://api.runpod.io/graphql` | GraphQL control plane (config key `apiUrl`). |
| `RUNPOD_INVOKE_URL` | `https://api.runpod.ai/v2` | Base URL for the Serverless invoke URLs reported by `serverless create/get/list/update` and the calls made by `serverless run/status/health` (config key `invokeUrl`). |

Invoke is a separate service from the control plane. Pointing `RUNPOD_API_URL` or `RUNPOD_GRAPHQL_URL` at a non-production host does not move the invoke URLs; override `RUNPOD_INVOKE_URL` explicitly when you need that.

## Shell completion

Enable tab completion for your shell to make working with `runpodctl` easier:

```bash
runpodctl completion
```

This command auto-detects your shell and adds the appropriate source command to your shell configuration file (`~/.bashrc` or `~/.zshrc`). The command is idempotent—running it again skips installation if completion is already configured.

Restart your shell or source the configuration file for changes to take effect.
