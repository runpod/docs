Sandboxes are short-lived, isolated CPU environments that you create on demand, run commands in, and tear down when you're done. They're built for running untrusted code: code generated by an AI agent, code submitted by your users, or one-off scripts you don't want touching your own infrastructure.

You manage sandboxes through the [REST API v2](/api-reference-v2/overview). Each sandbox runs a container image you choose, starts in seconds, and is billed per second until it terminates.

## When to use a sandbox

Use a sandbox when you need a clean, disposable environment for a short task:

- An AI agent needs to execute the code it writes.
- Your application runs code or commands supplied by end users.
- You want to test a script or package in isolation before running it elsewhere.

For long-running workloads, GPU compute, or persistent development environments, use [Pods](/pods/overview) instead. For request-driven inference that scales with traffic, use [Serverless](/serverless/overview).

## Isolation

Every sandbox runs under [gVisor](https://gvisor.dev/), a user-space kernel that intercepts the container's system calls. Code inside a sandbox can't reach the host machine or other tenants' sandboxes, so you can run code you don't trust.

## Lifecycle

A sandbox moves through these states:

| State | Meaning |
| --- | --- |
| `CREATING` | Compute is being allocated and the container image is being prepared. |
| `RUNNING` | Compute is allocated. The container may still be starting (see [Known limitations](#known-limitations)). |
| `TERMINATED` | The sandbox has stopped and its compute is released. Billing has stopped. |
| `FAILED` | The sandbox couldn't be created. |

`POST /v2/sandboxes` returns `201` with the new sandbox, usually still in the `CREATING` state. Poll `GET /v2/sandboxes/{id}` until `state` is `RUNNING` before you send commands.

### Termination is final

A terminated sandbox can't be restarted. Its record stays readable through `GET /v2/sandboxes/{id}`, with `terminationReason` and `terminatedAt` set, so you can see why and when it stopped. To run more work, create a new sandbox.

Terminating a sandbox that is already terminated succeeds, so it's safe to retry `DELETE /v2/sandboxes/{id}`.

## Timeouts

Every sandbox has two clocks. Whichever runs out first terminates the sandbox and stops billing:

- **Idle timeout** (`idleTimeoutSeconds`): how long the sandbox can go without activity. The deadline is reported in `idleExpiresAt` and moves forward with each activity, recorded in `lastActivityAt`.
- **Maximum lifetime** (`maxLifetimeSeconds`): a hard ceiling on total lifetime, counted from creation. The deadline is reported in `expiresAt`.

{/* TODO(DOCS-509): Confirm production values with Zack (AppConfig sandboxPolicyConfig). */}

| Setting | Default | Maximum |
| --- | --- | --- |
| Idle timeout | 10 minutes | 2 hours |
| Maximum lifetime | 1 hour | 24 hours |

If you omit either value, the default applies. If you request a value above the maximum, it's clamped to the maximum. Check `idleTimeoutSeconds` and `maxLifetimeSeconds` in the response to see the values actually applied.

<Tip>

Terminate sandboxes explicitly when you're finished, including in your error-handling paths. Don't rely on a timeout to stop billing.

</Tip>

## Network access

By default, a sandbox has **open outbound internet access**. Code inside it can reach any host on the internet, for example to install packages or call external APIs.

Restricting outbound traffic is opt-in. Set `egressMode` when you create the sandbox:

- `ALLOW_ALL`: open outbound access. This is the default.
- `ALLOW_LIST`: only the hosts listed in `egressAllowlist` are reachable.
- `DENY_ALL`: no outbound access.

If you're running untrusted code that doesn't need the internet, consider setting `egressMode` to `DENY_ALL`.

## Compute and pricing

Sandboxes run on CPU compute. You can set `cpuFlavorId`, `vcpuCount`, and `memoryInGb` when you create a sandbox, or omit them to use the standard sandbox configuration. The `compute` object in the sandbox response shows the vCPUs, memory, and container disk backing it.

Sandboxes are billed per second from creation until termination, at the rate shown in `compute.costPerHr` (USD per hour). Your account needs enough balance to start a sandbox; otherwise, create returns `402`.

## Labels

Attach `labels` (string key-value pairs) when you create a sandbox to track which job, user, or environment it belongs to. You can filter `GET /v2/sandboxes` by one or more labels, written as `key=value`.

## Known limitations

These limitations reflect current behavior and will change as the feature matures:

- **The first command can return `409`.** `RUNNING` means compute is allocated, not that the container has finished starting. For about 10 to 30 seconds after a sandbox reaches `RUNNING`, `exec` and `logs` can return `409`. Retry with a short backoff.
- **Command output arrives when the command finishes.** `exec` returns combined stdout and stderr in a single `output` field, plus an `error` field, only after the command completes. There is no separate exit code yet.
- **Long-running commands are cut off.** Each `exec` call has a short execution cap. For longer work, start the process in the background and poll for its result:

  ```json
  {"command": ["sh", "-c", "setsid nohup python job.py > /tmp/job.log 2>&1 &"]}
  ```

  Then read `/tmp/job.log` with later `exec` calls.
