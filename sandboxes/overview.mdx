Sandboxes are short-lived, isolated CPU environments that you create on demand, run commands in, and tear down when you're done. They're built for running untrusted code: code generated by an AI agent, code submitted by your users, or one-off scripts you don't want touching your own infrastructure.

You manage sandboxes through the [REST API v2](/api-reference-v2/overview). Each sandbox runs a container image you choose, a Runpod template or the default image, and is billed per second until it terminates.

## When to use a sandbox

Use a sandbox when you need a clean, disposable environment for a short task:

- An AI agent needs to run the code it writes.
- Your application runs code or commands supplied by end users.
- You want to test a script or package in isolation before running it elsewhere.

For long-running workloads, GPU compute, or persistent development environments, use [Pods](/pods/overview) instead. For request-driven inference that scales with traffic, use [Serverless](/serverless/overview).

## Use sandboxes with a coding agent

The fastest way to start is to let your coding agent set things up. In the [Runpod console](https://console.runpod.io/sandboxes), open **Sandboxes** and select **Setup guide**. It gives you:

- An API key for your agent to read from `RUNPOD_API_KEY`.
- A prompt to paste into Claude Code, Codex, Cursor or another coding agent. The agent learns the API, creates a sandbox, runs a command and cleans up.
- A skill file you can add to your agent.

## Isolation

Every sandbox runs under [gVisor](https://gvisor.dev/), a user-space kernel that intercepts the container's system calls. Code inside a sandbox can't reach the host machine or other users' sandboxes, so you can run code you don't trust.

## Images and templates

You can start a sandbox in three ways:

- **Default image:** send an empty request body (`{}`) and the sandbox runs Runpod's default sandbox image.
- **Template:** set `templateId` to a Runpod sandbox template. Templates start fastest because their images are cached on Runpod hosts.
- **Container image:** set `image` to any container image, for example `python:3.12-slim`. For a private image, also set `registry` to the ID of one of your saved container registry credentials (from `/v2/registries`). Your own images start slower the first time, because they have to be downloaded (see [Cold starts](#cold-starts)).

`image` and `templateId` can't be used together.

Runpod provides these sandbox templates:

| Template | Template ID | Use it for |
| --- | --- | --- |
| Ubuntu | `TEMPLATE_ID` | A general-purpose Linux environment. |
| Browser | `n2mv38hebo` | Headless browser work: screenshots, UI checks and end-to-end tests with Playwright and Chromium. |
| Harbor | `TEMPLATE_ID` | Running Harbor agent evaluations. |
| OpenClaw | `TEMPLATE_ID` | Running the OpenClaw agent. |

If you start a sandbox from an image without a start command, it runs a keepalive process so it stays up for you to run commands in. To run your own main process, set `cmd` (and optionally `entrypoint`) in exec form, for example `["python", "-m", "http.server", "8080"]`. When that process exits, the container stops and the sandbox no longer accepts commands, so use a long-running process.

## Cold starts

A cold start is the time from your create request to the first command that succeeds. Most of it is spent downloading the container image and starting the container on a host.

To get the fastest start:

- **Use a Runpod template or the default image.** Their images are cached on Runpod hosts, so they don't need to be downloaded.
- **Expect a slower first start with your own image.** It has to be downloaded to the host the first time it runs there. Smaller images download faster.
- **Wait for the sandbox to accept commands.** A sandbox can report `RUNNING` a few seconds before its container is ready. Until then, commands return `409` with code `sandbox_starting`, so retry after a short delay.

Runpod is working to make cold starts shorter.

## Lifecycle

A sandbox moves through these states:

| State | Meaning |
| --- | --- |
| `CREATING` | Compute is being allocated. |
| `RUNNING` | Compute is up. The container may still be starting, so commands can briefly return `409` with code `sandbox_starting`. |
| `TERMINATED` | The sandbox has stopped. `terminationReason` says why. Billing has stopped. |
| `FAILED` | The sandbox couldn't start, for example because no capacity was available or the image couldn't be pulled. It isn't billed. |

`POST /v2/sandboxes` returns `201` with the new sandbox, usually still in the `CREATING` state. Poll `GET /v2/sandboxes/{id}` until `state` is `RUNNING` before you send commands.

`terminationReason` is one of these values (more may be added):

| Value | Meaning |
| --- | --- |
| `USER_REQUESTED` | You terminated the sandbox. |
| `IDLE_TIMEOUT` | The sandbox reached its idle timeout. |
| `MAX_LIFETIME` | The sandbox reached its maximum lifetime. |
| `FAILED` | The create failed. |
| `ADMIN_TERMINATED` | Runpod terminated the sandbox. |
| `RECONCILED` | Its compute was stopped outside the sandbox API. |

### Retry creates safely

Send an `Idempotency-Key` header with each create request. If the response is lost and you retry with the same key and the same body, the API returns the sandbox the first request created instead of creating, and billing for, a second one.

- If the create was rejected for its input or because you've reached the sandbox limit (`400`), the key isn't used, so you can retry with it.
- If the create was accepted and then failed, for example because no capacity was available or the image couldn't be pulled, the key is spent. Every retry with it returns `409`, so retry with a new key.

### Termination is final

A terminated sandbox can't be restarted. To run more work, create a new sandbox. You can still read a terminated sandbox with `GET /v2/sandboxes/{id}` for a while, but don't depend on it staying available.

Terminating a sandbox that's already terminated succeeds, so it's safe to retry `DELETE /v2/sandboxes/{id}`.

## Timeouts

Every sandbox has two timeouts. Whichever runs out first terminates the sandbox and stops billing.

| Timeout | Field | Default | Minimum | Maximum |
| --- | --- | --- | --- | --- |
| Idle timeout: how long the sandbox can go without activity | `idleTimeoutSeconds` | 10 minutes (600) | 90 seconds | 2 hours (7200) |
| Maximum lifetime: total time from creation | `maxLifetimeSeconds` | 1 hour (3600) | | 24 hours (86400) |

On create, values above the maximum are lowered to it and idle timeouts under 90 seconds are raised to 90. The response shows the values that were applied. The idle timeout can't be turned off. The deadlines are reported in `idleExpiresAt` and `expiresAt`.

To change the timeouts of a running sandbox:

- [Update a sandbox](/api-reference-v2/sandboxes/update-a-sandbox) (`PATCH /v2/sandboxes/{id}`) to raise or lower either timeout.
- [Extend a sandbox's lifetime](/api-reference-v2/sandboxes/extend-a-sandbox) (`POST /v2/sandboxes/{id}/extend`) to raise the maximum lifetime only.

### What counts as activity

These reset the idle timer:

- A command that the sandbox accepts, through exec or the commands API, whatever its exit code.
- Reading a command's status or output.
- An open log stream, for the sandbox or a command.

These **don't** reset the idle timer:

- A process that's already running inside the sandbox, such as a server you started.
- An SSH session.
- Traffic to the sandbox's ports.

Activity is recorded at most once every 30 seconds. If your sandbox runs a long job or serves traffic, set a longer `idleTimeoutSeconds` or keep sending activity, otherwise it's terminated as idle.

<Tip>

Terminate sandboxes explicitly when you're finished, including in your error-handling code. Don't rely on a timeout to stop billing.

</Tip>

## Run commands

There are two ways to run a command in a sandbox. Both take the command as an argv array, for example `["python", "script.py"]`. Commands aren't run through a shell, so wrap them in `["sh", "-c", "..."]` to use pipes, redirects or `&&`.

| | [Exec](/api-reference-v2/sandboxes/run-a-command-in-a-sandbox) | [Commands](/api-reference-v2/sandboxes/start-a-command-in-a-sandbox) |
| --- | --- | --- |
| Use it for | Short commands where you want the result in the same request | Builds, test suites, servers and other long-running work |
| How it works | Waits for the command to finish and returns its output and exit code | Returns as soon as the command starts. Check its status and read its output with later requests, or cancel it. |
| Time limit | Up to `timeoutSeconds` (default 30, max 50). On some sandboxes the limit is lower. | Up to `timeoutSeconds` (default 1 hour, max 24 hours) |
| Output | Up to 4 MiB in the response | Up to 32 MiB, readable for about 20 minutes after the command finishes |

Both accept `cwd` (the directory to run in) and `env` (environment variables for that command only). A sandbox runs at most **8 commands at once** through the commands API.

## Network access

By default, a sandbox has **open outbound internet access**. Code inside it can reach any host on the internet, for example to install packages or call external APIs.

Restricting outbound traffic isn't available yet. The `egressMode` and `egressAllowlist` fields are accepted and stored, but not enforced, and any mode other than `ALLOW_ALL` returns `400` until restriction is enabled for your account.

## Exposed ports

To reach a web service running inside a sandbox, list its ports in `ports` when you create the sandbox (up to 15):

```json
{"ports": [{"port": 8080, "protocol": "http"}]}
```

Each `http` port is reached through the Runpod proxy at the `url` returned in the sandbox's `ports` list. Treat the URL as opaque.

Only `http` ports are available today. `tcp` and `udp` ports return `400`.

## Storage

Each sandbox has an ephemeral container disk, 10 GB by default. Set `disk` to change it, up to a limit that depends on the CPU flavor and vCPU count. The container disk is deleted when the sandbox terminates.

To keep data after the sandbox ends, or to share it between sandboxes, mount a volume with `mounts`. You can mount at most one of each type:

- **Network volume** (`mounts.network`): a [network volume](/storage/network-volumes), mounted at `/workspace` by default. A network volume lives in one data center, so the sandbox is placed there. Create the volume in a data center that offers sandboxes.
- **Global volume** (`mounts.global`): a global volume, mounted at `/workspace-global` by default. It isn't tied to a data center, and every sandbox that mounts it sees the same files.

```json
{"mounts": {"global": [{"volumeId": "YOUR_VOLUME_ID", "path": "/workspace-global"}]}}
```

Keep code, repositories and scripts on the container disk, and use volumes for data. See [Known limitations](#known-limitations) for current volume restrictions.

## Move data in and out

There's no file upload or download API yet, and you can't stream data into a sandbox. Use one of these instead:

| Method | Best for | How |
| --- | --- | --- |
| **S3-compatible API on a volume** | Moving files of any size, from code | Mount a global volume or network volume and write to it with its S3-compatible API from outside the sandbox. The files appear in the mounted path inside the sandbox. |
| **Mounted volume** | Data you want to keep after the sandbox ends | Mount the volume with `mounts` and read and write it as a normal directory. |
| **Commands** | Small files and text | Send the content in a command. Each request body is limited to 1 MiB, so split larger data into chunks. |
| **Download from inside** | Public files, packages and repos | Run `curl`, `pip`, `git clone` and similar tools inside the sandbox. Sandboxes have open outbound internet access. |

Volumes are slow when you write many small files, so use them for larger data files.

## Connect over SSH

Set `startSsh: true` on create to add the SSH public keys registered on your account to the sandbox. You need registered keys first; without them, the flag does nothing. Connect through the Runpod proxy using the details in the sandbox's `ssh` field.

Only images that start `sshd` from the `PUBLIC_KEY` environment variable support this. All Runpod official images do.

## Environment variables and secrets

Pass environment variables in `env`. You can reference a [Runpod secret](/pods/templates/secrets) with `{{ RUNPOD_SECRET_name }}`. A create that references a secret you can't access is rejected.

`env`, `cmd` and `entrypoint` together must fit in about 100 KB, otherwise create returns `413`.

<Warning>

`env` is returned as written in API responses, so anyone who can read the sandbox can see plain values. Use secret references for credentials instead of plain values.

</Warning>

## Compute and pricing

Sandboxes run on CPU compute. Set the CPU flavor and vCPU count in `cpu`, or omit it to get the default sandbox flavor with 2 vCPUs. `vcpuCount` must be a power of two (2, 4, 8, 16 or 32), and memory and container disk scale with the flavor. The `cpu` and `compute` fields in the response show what the sandbox is running on.

Sandboxes are billed per second from creation until they terminate, at the rate in `compute.costPerHr` (USD per hour). The default size, 2 vCPU and 4 GB of memory, costs **$0.14 per hour**. Your account needs enough balance to start a sandbox, otherwise create returns `402`.

Sandbox spend appears as its own line in your billing summary and CSV export.

## Labels

Attach `labels` (string key-value pairs) when you create a sandbox to track which job, user, or environment it belongs to. You can add up to 20 labels. Keys can be up to 64 letters, numbers, `_` or `-`, and values up to 255 characters.

You can filter `GET /v2/sandboxes` by one or more labels, written as `key=value`.

## Known limitations

Sandboxes are in beta. These limitations reflect current behavior and will change:

- **Commands can return `409` right after the sandbox reports `RUNNING`.** The container may still be starting. Retry when the code is `sandbox_starting`.
- **Only HTTP ports work.** `tcp` and `udp` ports return `400`, so you can only connect over SSH through the Runpod proxy, not directly.
- **Network volumes can't be written to in some data centers yet.** Use a global volume until this is fixed. On a network volume, a process that doesn't run as root can't create files.
- **Global volumes don't support every file operation.** `chmod` and `utime` fail, files can't be made executable, and `git init` fails.
- **Outbound traffic can't be restricted yet.** `egressMode` and `egressAllowlist` are stored but not enforced.
- **Use an API key with full access.** Scoped API keys don't work with sandboxes yet.
- **Creating many sandboxes at the same time can fail.** If a create fails, retry it with a new `Idempotency-Key`.
- **A sandbox can keep billing after its container exits.** If a command returns `409` with code `container_exited`, terminate the sandbox and create a new one.
- **`/tmp` uses memory.** Large files in `/tmp` count against the sandbox's memory and can stop it. Write large files to your home directory or a volume.
- **Cost centers and projects don't support sandboxes yet.**
