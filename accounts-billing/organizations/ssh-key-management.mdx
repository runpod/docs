Each member of your organization adds their own SSH public key in their Runpod account settings. Runpod injects those keys into the organization's Pods and keeps them in sync. Running Pods pick up key changes and membership changes without a redeploy.

Members add keys on the same account settings page whether they belong to a team or an organization. There is no separate organization keys page. Runpod combines members' keys for each Pod, which gives your team consistent access across the organization's Pods without per-Pod key setup.

## How key injection works

Runpod writes the public keys of everyone with access to a Pod into that Pod's `/root/.ssh/authorized_keys` file. The host machine checks the key set continuously, so a key change usually reaches running Pods in under a minute. Runpod also rewrites the file when the Pod restarts and every 15 minutes, even when no key has changed.

Runpod manages the entire `authorized_keys` file. Any key you add to the file manually from inside the Pod is removed at the next sync. To give someone SSH access, add their key to their account settings or add them to the organization instead.

The key set comes from account settings only. The `PUBLIC_KEY` and `RUNPOD_SSH_PUBLIC_KEY` environment variables no longer change which keys can connect over SSH via public IP. If a Pod sets either variable, Runpod replaces that key with the account keys at the next sync.

Key injection applies to Pods, including the nodes of [Instant Clusters](/instant-clusters). It does not apply to Serverless workers, which use only the endpoint owner's keys.

### Connection methods

The two SSH connection methods apply key changes at different times.

With proxied SSH through `ssh.runpod.io`, Runpod checks your key against your current account settings each time you log in. A key you add or delete takes effect at your next login.

With SSH via public IP, you connect directly to the SSH daemon inside the Pod, which reads `authorized_keys`. Key changes take effect after the next sync, usually within a minute.

For both methods, SSH sessions that are already open stay open after a key is deleted or a member is removed.

## Who receives keys

A Pod receives the keys of the same people who can see it in the console.

A personal Pod receives its owner's keys. By default, an organization Pod receives the keys of the member who created the Pod, members who share a [group](/organizations/orgs-groups) with them, and organization admins. If your organization lets every member see all resources, every member's keys are injected.

When a member joins the organization, their keys reach the Pods they can see at the next sync. When a member leaves, their keys are removed from those Pods at the next sync.

## Roles and permissions

Members with any of these roles can add and delete their own SSH keys. Runpod injects each member's keys into the organization's Pods that member can see:

- Admin.
- Dev.
- Basic.

The Billing role does not manage SSH keys through the console. However, Runpod still injects a Billing member's public key into the organization's Pods they can see. To remove someone's SSH access, remove them from the organization.

For the full role matrix, see [Roles and permissions](/accounts-billing/organizations/roles-and-permissions).

## Add an SSH key

<Steps>
  <Step title="Generate a key pair">
    If you don't already have an SSH key pair, generate one on your local machine. Runpod stores only the **public key**. Never paste your private key anywhere.

    <Tabs>
    <Tab title="macOS / Linux">
    ```bash
    ssh-keygen -t ed25519 -C "your-name@yourorg.com"
    ```

    When prompted, accept the default file location (`~/.ssh/id_ed25519`) or specify a custom path. To view your public key:

    ```bash
    cat ~/.ssh/id_ed25519.pub
    ```
    </Tab>
    <Tab title="Windows (PowerShell)">
    ```powershell
    ssh-keygen -t ed25519 -C "your-name@yourorg.com"
    ```

    When prompted, accept the default file location. To view your public key:

    ```powershell
    Get-Content "$env:USERPROFILE\.ssh\id_ed25519.pub"
    ```

    If `ssh-keygen` is not available, install [OpenSSH for Windows](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_install_firstuse) or use [PuTTYgen](https://www.puttygen.com/).
    </Tab>
    </Tabs>

    Your public key looks like:

    ```text
    ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... your-name@yourorg.com
    ```
  </Step>
  <Step title="Add the public key to your account">
    Paste your public key into the **SSH Public Keys** field in your [Runpod account settings](https://www.console.runpod.io/user/settings). This is the same field for team and organization members. There is no organization-specific keys page. For the full procedure, including the CLI method, see [Generate an SSH key and add it to your Runpod account](/pods/configuration/use-ssh#generate-an-ssh-key-and-add-it-to-your-runpod-account).

    To confirm the key was saved, run `runpodctl ssh list-keys`.

    Runpod injects your new key into the Pods you can see at the next sync, usually within a minute. You don't need to redeploy running Pods.
  </Step>
</Steps>

## Manage your keys

You add and delete your own keys from the **SSH Public Keys** field in your [Runpod account settings](https://www.console.runpod.io/user/settings). Paste each key on its own line to add it, and delete its line to remove it. Renaming a key is not supported.

When you delete a key, Runpod removes it from running Pods at the next sync. Proxied SSH stops accepting the key at your next login.

## Connect to a Pod

Connecting to an organization's Pod works the same as connecting to any other Pod: you connect with the private key that matches one of the public keys injected into the Pod. For the connection methods, including basic proxied SSH, full SSH over public IP, and password-based access, see [Connect to a Pod with SSH](/pods/configuration/use-ssh).

## Troubleshooting

**Permission denied (publickey)**

Confirm that the matching public key is in your account settings. Then check that you pass the right private key to SSH with `-i`. If you added the key in the last minute, wait for the next sync and try again. If the error continues, check the key's format. For common format issues, see [Connect to a Pod with SSH](/pods/configuration/use-ssh#troubleshooting-ssh-key-authentication).

**Connected to the wrong Pod**

Copy the IP and port fresh from the **Connect** tab. They may change when you stop and resume the Pod.

**A key added inside the Pod stopped working**

Runpod manages the Pod's `authorized_keys` file and removes keys added from inside the Pod at the next sync. Add the key to your account settings instead.

**SSH via public IP doesn't work on a Pod deployed without keys**

If no SSH keys were available when the Pod was deployed, the Pod might not start its SSH daemon. Add your key to your account settings, then redeploy the Pod (terminate it and deploy a new one).

<Warning>
Terminating a Pod permanently deletes any data that is not stored on a [network volume](/storage/network-volumes). Back up your data or attach a network volume before you terminate a Pod.
</Warning>

**Member can't connect to a Pod**

Confirm that the member can see the Pod in the console. A Pod receives only the keys of members who can see it (see [Who receives keys](#who-receives-keys)).

## Security notes

**Store only public keys.** Never paste a private key into Runpod. Your private key stays only on the machine you connect from.

**Use a strong key type.** An ed25519 key (`-t ed25519`) is recommended.

**Rotate keys regularly.** If a key may be compromised, delete it from your account settings and generate a new key pair. Runpod removes the deleted key from running Pods at the next sync. After a Pod restarts, the deleted key can still connect for up to about 30 seconds, until the first sync completes.

**Offboarding members.** When you remove a member from the organization, Runpod removes their keys from the organization's Pods at the next sync. Proxied SSH rejects their keys at their next login. Key removal doesn't close SSH sessions that are already open. To end them, restart the affected Pods.

**Know what key sync controls.** Key sync manages only the `authorized_keys` file. It doesn't undo other access that a former member set up inside a Pod. For example, they might have created another user account, changed `sshd_config`, or added a scheduled job. If a former member had SSH access to a Pod that holds sensitive data, review the Pod or redeploy it.
