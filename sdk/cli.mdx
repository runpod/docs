The `rp` CLI is installed with the `runpod` Python package. Use it to authenticate, develop and deploy apps, compare hardware pricing and stock, and work with Serverless endpoints, Pods, volumes, and SSH keys. The same CLI is also available under the name `runpod`, so `rp flash deploy` and `runpod flash deploy` are equivalent.

<Note>
  The `rp` CLI is separate from [`runpodctl`](/runpodctl/overview), which is a standalone binary with a different set of commands.
</Note>

## Command summary

```bash
# Auth
rp login

# Apps
rp flash init my-app
rp flash dev main.py
rp flash deploy
rp flash app list
rp flash env list --app my-app
rp flash undeploy --app my-app

# Secrets and registries
rp secret add SECRET_NAME
rp registry add REGISTRY_NAME

# Logs and updates
rp logs POD_ID --follow
rp update

# SSH
rp ssh add
rp ssh list
rp ssh POD_ID

# Pods
rp pod list
rp pod create my-pod --gpu 4090 --image runpod/pytorch:latest --ssh --wait
rp pod stop POD_ID
rp pod connect POD_ID

# Serverless endpoints
rp endpoint list
rp endpoint create --name my-endpoint --type queue --image IMAGE --gpu 4090
rp endpoint run ENDPOINT_ID --data '{"prompt": "hello"}'
rp endpoint logs ENDPOINT_ID --follow

# Hardware pricing and stock
rp catalog h100

# Volumes
rp volume list
rp volume create --name models --size 100 --region eu
rp volume delete VOLUME_ID

# Shell completion
rp completion zsh
```

App lifecycle commands live under `rp flash`. All other commands live at the root. Run `rp --help` or `rp COMMAND --help` for details on any command.

## rp login

Authenticate with Runpod and save your credentials to `~/.runpod/config.toml`:

```bash
rp login                       # Approve access in your browser
rp login --api-key API_KEY     # Store a key directly
rp login --profile staging     # Save credentials to a named profile
```

Use `--profile PROFILE_NAME` with either login method to update only that profile. The default profile is `default`. To print the approval URL instead of opening a browser, add `--no-open`.

## rp flash init

Scaffold a new app project:

```bash
rp flash init my-app   # Create a project in a new my-app directory
rp flash init .        # Create a project in the current directory
```

This writes `main.py` (an app with one queue function and a local entrypoint), `requirements.txt`, and `.runpodignore`. Existing files aren't overwritten unless you add `--force`. See [Build an app](/sdk/apps/build-app).

## rp flash dev

Run a live development session for the app defined in a file:

```bash
rp flash dev main.py
```

The session creates temporary endpoints, runs the function marked with `@runpod.local_entrypoint`, and streams worker logs back to your terminal. Edit your code, then press Enter to re-run. Workers pick up the new code automatically.

See [Dev sessions](/sdk/apps/dev-sessions) for how sessions work. To run the entrypoint once and exit, which is useful for scripts and CI, add `--once`:

```bash
rp flash dev main.py --once
```

When you press Ctrl-C, the session waits for the running entrypoint to finish and then deletes its endpoints. If cleanup fails, the command exits with an error and lists the endpoint IDs you need to delete.

<Tip>
  App discovery imports your modules synchronously. Keep blocking work inside an entrypoint or a remote function. If discovery hangs on an import, interrupt it with Ctrl-C.
</Tip>

## rp flash deploy

Build and deploy the app in the current project:

```bash
rp flash deploy
```

This packages and deploys every app found in the current directory. To deploy another directory, pass its path, for example `rp flash deploy path/to/project`. Flags:

| Flag | Description |
| --- | --- |
| `--env`, `-e` | Deploy to a specific environment. Defaults to the app's environment, which is `default` unless set in code. |
| `--exclude PACKAGES` | Leave a comma-separated list of packages out of the artifact, for example `--exclude scipy,pandas`. They must then come from the worker image. |
| `--python-version VERSION` | The worker Python version used to pick dependency wheels, from 3.10 to 3.14. Defaults to the Python running the CLI. |
| `--build-only` | Build the artifact without deploying it, and write `APP_NAME-artifact.tar.gz` to the current directory. This replaces `flash build`. |

To learn what goes into the artifact, including ignore rules and the size limit, see [Deploy an app](/sdk/apps/deploy).

## rp flash app

Manage the apps you've deployed:

```bash
rp flash app list              # List your apps
rp flash app get APP_NAME      # Show an app's details
rp flash app delete APP_NAME   # Delete an app (add --yes to skip the prompt)
```

## rp flash env

Manage an app's environments, such as `dev`, `staging`, and `production`:

```bash
rp flash env list --app my-app       # List environments
rp flash env get ENVIRONMENT_NAME    # Show an environment's endpoints and status
rp flash env add ENVIRONMENT_NAME    # Create an environment
rp flash env delete ENVIRONMENT_NAME # Delete an environment
```

The `env` commands use the app in the current directory. If the directory has no app or more than one, pass `--app APP_NAME`.

## rp flash undeploy

Delete an environment's endpoints and the environment itself:

```bash
rp flash undeploy --app my-app              # Undeploy the default environment
rp flash undeploy --app my-app --env staging
```

The app and its build history remain. `--app` is optional when the current directory has one app. Add `--yes` to skip the confirmation prompt.

<Warning>
  Undeploying an app doesn't delete network volumes it created. Volumes continue to incur storage charges until you delete them with [`rp volume delete`](#rp-volume).
</Warning>

## Secrets and registries

Store secrets that your app reads with `runpod.Secret`, and save credentials for private container registries:

```bash
rp secret add SECRET_NAME       # Create a secret (prompts for the value)
rp secret list                  # List secrets
rp secret delete SECRET_NAME    # Delete a secret

rp registry add REGISTRY_NAME   # Save registry credentials (prompts for username and password)
rp registry list                # List saved credentials
rp registry delete REGISTRY_NAME
```

`rp secret add` also accepts `--value` and `--description`, and `rp registry add` accepts `--username` and `--password`. If you leave them out, the CLI prompts for them, which keeps the values out of your shell history. Reference a secret in code with `env={"HF_TOKEN": runpod.Secret("SECRET_NAME")}`, and registry credentials with `registry_auth="REGISTRY_NAME"`.

## rp logs

Show a Pod's container and system logs, such as a Pod started by `@app.task`:

```bash
rp logs POD_ID                    # Show recent logs
rp logs POD_ID --follow           # Stream new logs as they arrive
rp logs POD_ID --tail 500         # Backfill the last 500 lines (default 100)
rp logs POD_ID --type container   # Only container logs (all, container, or system)
```

## rp update

Update the `runpod` package, which includes the CLI, to the latest version:

```bash
rp update
rp update --version 2.0.0   # Install a specific version
```

## rp ssh

Manage SSH keys on your account and connect to Pods:

```bash
rp ssh add       # Add a key to your account
rp ssh list      # List the keys on your account
rp ssh POD_ID    # Open a terminal on a Pod
```

`rp ssh add` generates a new key if you don't pass one. To use an existing key, pass `--key` or `--key-file`. Keys are stored in `~/.runpod/ssh/`.

## rp pod

Create, manage, and connect to Pods:

```bash
rp pod list                                  # List your Pods
rp pod get POD_ID                            # Show a Pod with its connection details
rp pod create my-pod --gpu 4090 --image runpod/pytorch:latest --ssh --wait
rp pod update POD_ID --env DEBUG=1           # Change a Pod's settings
rp pod stop POD_ID                           # Stop a running Pod
rp pod start POD_ID --wait                   # Start a stopped Pod and wait until it's running
rp pod restart POD_ID                        # Restart a running Pod
rp pod terminate POD_ID                      # Delete a Pod permanently (alias: rp pod delete)
rp pod logs POD_ID --follow                  # Stream a Pod's logs
rp pod connect POD_ID                        # Open a terminal on a Pod over SSH
rp pod sync SOURCE_POD_ID DEST_POD_ID        # Copy /workspace from one Pod to another
```

If you leave out `POD_ID`, the CLI prompts you to pick a Pod. In a non-interactive shell, such as a script or CI job, pass the ID. Add `--json` to `list`, `get`, `create`, `update`, `start`, `stop`, `restart`, or `logs` to print JSON for use in scripts. Status messages and warnings go to stderr, so stdout holds only the JSON.

To filter `rp pod list`, add `--name TEXT` to match part of a Pod's name, or `--status STATUS` to show Pods in one status, such as `running` or `exited`. Repeat `--status` to include more than one. To include Pods that belong to an Instant Cluster, add `--include-cluster-pods`.

### Create a Pod

`rp pod create` takes a Pod name, the hardware, and a container image or template:

```bash
rp pod create trainer --gpu h100:2 --image runpod/pytorch:latest --region eu --ssh
rp pod create box --cpu cpu3c --vcpu 4 --image ubuntu:24.04
rp pod create notebook --gpu 4090 --image runpod/pytorch:latest --jupyter -p 8888/http
```

For a GPU Pod, pass `--gpu` with a GPU name such as `4090`, `h100`, or `a100-sxm`, and optionally a count, such as `h100:2`. When a name matches more than one GPU type, the CLI picks the one with the most stock in the data centers you allow. Ties go to the lowest price, and the CLI prints the type it chose. If the catalog shows no stock for the GPU, the CLI warns you that creation may fail. To compare options before you create a Pod, run [`rp catalog`](#rp-catalog).

For a CPU Pod, pass `--cpu` with a CPU type such as `cpu3c` or `cpu5c`. `--vcpu` sets the number of vCPUs, starting at 2. If you leave it out, the Pod gets the CPU type's minimum.

| Flag | Description |
| --- | --- |
| `--gpu TYPE[:COUNT]` | The GPU type and, optionally, the number of GPUs. |
| `--gpu-count N` | The number of GPUs, if you don't include it in `--gpu`. Defaults to 1. |
| `--cpu TYPE` | The CPU type, for a CPU Pod. You can't combine it with `--gpu`. |
| `--vcpu N` | The number of vCPUs for a CPU Pod. |
| `--cloud TIER` | `secure` or `community`. Defaults to Secure Cloud. |
| `--region REGION` | A region such as `eu`, `na`, or `asia`, a data center ID prefix such as `us` or `eu-ro`, or a data center ID. Repeat the flag to include more than one. |
| `--data-center ID` | An exact data center ID, such as `US-TX-3`. Repeat the flag to include more than one. |
| `--cuda VERSION` | The host CUDA version. Use `'>=12.4'` for a minimum version, or `12.4` or `12.4,12.8` for exact versions. GPU Pods only. |
| `--min-ram-per-gpu GB` | The minimum host RAM per GPU, in GB. GPU Pods only. |
| `--min-vcpu-per-gpu N` | The minimum host vCPUs per GPU. GPU Pods only. |
| `--ssh` | Start an SSH server that accepts the SSH keys on your account. If your account has no keys, the CLI warns you. Add one with [`rp ssh add`](#rp-ssh). |
| `--jupyter` | Start JupyterLab. Expose port 8888 with `-p 8888/http` to reach it. |
| `--wait` | Wait until the Pod's container is running, for up to 10 minutes. |

If you don't pass `--region` or `--data-center` but do attach a network volume, the CLI places the Pod in the volume's data center.

### Container settings

`rp pod create` and `rp pod update` share these flags for the Pod's container:

| Flag | Description |
| --- | --- |
| `--image IMAGE` | The container image, such as `runpod/pytorch:latest`. |
| `--template ID` | A template ID whose container settings to apply. |
| `--env`, `-e KEY=VALUE` | An environment variable. Repeat the flag to set more than one. |
| `--port`, `-p PORT/PROTOCOL` | A port to expose, such as `8888/http` or `22/tcp`. Repeat the flag to expose more than one. |
| `--disk GB` | The container disk size, in GB. |
| `--persistent-volume GB[:PATH]` | A volume disk on the Pod's host, such as `50` or `50:/workspace`. The mount path defaults to `/workspace`. |
| `--network-volume ID[:PATH]` | A [network volume](/storage/network-volumes) to attach. The mount path defaults to `/workspace`. |
| `--global-volume ID[:PATH]` | A [global volume](/storage/globalvolume/overview) to attach. |
| `--cmd COMMAND` | The container `CMD`, as a shell string. |
| `--entrypoint COMMAND` | The container `ENTRYPOINT`, as a shell string. |
| `--args COMMAND` | The container start command, as one string. Pass `''` to clear it. |
| `--registry NAME` | The name or ID of saved [registry credentials](#secrets-and-registries) for a private image. Pass `''` to clear it. |
| `--global-networking` | Turn on private networking between Pods across data centers. NVIDIA GPUs only. Use `--no-global-networking` to turn it off. |

`rp pod create` needs either `--image` or `--template`.

### Update a Pod

`rp pod update` changes a Pod's name with `--name`, its container settings, and its lock. Most changes take effect the next time the Pod starts.

`--env` adds or replaces variables in the Pod's existing environment, and `--unset-env KEY` removes one. `--port` replaces the full list of exposed ports. A volume flag restates the whole mount: you can change its size or mount path, but not the volume ID. If you leave out the path, the Pod keeps the current one.

`--lock` keeps anyone from stopping or resetting the Pod until you run `rp pod update POD_ID --unlock`.

### Start, stop, and terminate a Pod

`rp pod stop` stops a running Pod and keeps its volume. `rp pod start` starts a stopped Pod, and `rp pod restart` restarts a running one. Add `--wait` to `start` or `restart` to return once the container is running.

<Warning>
  `rp pod terminate` permanently deletes a Pod, including its container disk and volume disk. Network volumes and global volumes attached to the Pod aren't deleted. The CLI asks you to confirm. Add `--yes` to skip the prompt. A non-interactive shell requires `--yes`.
</Warning>

### Read logs and connect

`rp pod logs` shows a Pod's container and system logs. These flags change what it shows:

- `--follow` streams new lines as they arrive.
- `--tail N` sets how many earlier lines to show, up to 5000. The default is 100.
- `--source container` or `--source system` shows only one source.
- `--since TIMESTAMP` shows only lines after a time.

`rp pod connect` opens a terminal on a Pod over SSH, like `rp ssh POD_ID`. It needs an SSH key on your account and port `22/tcp` exposed on the Pod. `rp pod get` also prints the SSH command and the proxy URLs for the Pod's HTTP ports.

`rp pod sync SOURCE_POD_ID DEST_POD_ID` copies `/workspace` on the source Pod into a new `sync_XXXXXXXX` folder in `/workspace` on the destination Pod, so existing files aren't overwritten. To copy other directories, pass the source and destination paths after the Pod IDs. Both Pods need SSH access.

## rp endpoint

Create, configure, and call Serverless endpoints, and watch their workers and logs:

```bash
rp endpoint list --type queue                # List queue endpoints
rp endpoint get ENDPOINT_ID                  # Show an endpoint's configuration
rp endpoint create --name llama-prod --type queue --image ghcr.io/acme/llama:latest --gpu h100
rp endpoint update ENDPOINT_ID --env DEBUG=1 --wait
rp endpoint edit ENDPOINT_ID                 # Edit the configuration in your editor
rp endpoint scale ENDPOINT_ID --max-workers 8
rp endpoint workers ENDPOINT_ID --watch      # Watch worker status
rp endpoint releases ENDPOINT_ID             # Show release history and rollout progress
rp endpoint logs ENDPOINT_ID --follow        # Stream logs from every worker
rp endpoint run ENDPOINT_ID --data '{"prompt": "hello"}'
rp endpoint job wait ENDPOINT_ID JOB_ID      # Wait for a queued job's output
rp endpoint purge ENDPOINT_ID                # Remove every queued job
rp endpoint delete ENDPOINT_ID               # Delete an endpoint and its workers
```

If you leave out `ENDPOINT_ID` from `rp endpoint get` or `rp endpoint edit`, the CLI prompts you to pick an endpoint. Other commands need the ID, and [shell completion](#rp-completion) fills it in. Add `--json` to any command except `delete` to print JSON for use in scripts.

To filter `rp endpoint list`, add `--name` to match an endpoint name, including wildcards such as `'llama*'`, or `--type queue` or `--type load-balancer`. Names aren't unique, so the results always include IDs.

### Create an endpoint

`rp endpoint create` needs a name, an endpoint type, the hardware, and a container image or template:

```bash
# Queue endpoint on H100 GPUs in Europe
rp endpoint create --name llama-prod --type queue \
  --image ghcr.io/acme/llama:latest --gpu h100 --max-workers 4 \
  --region eu --env MODEL_ID=meta-llama/Llama-3.1-8B --flashboot standard

# Load balancing endpoint that sends each worker up to 4 requests
rp endpoint create --name openai-api --type load-balancer \
  --image ghcr.io/acme/openai-server:latest --gpu 4090 \
  --requests-per-worker 4 --env PORT=8000

# CPU endpoint with 8 vCPUs per worker
rp endpoint create --name embeddings --type queue \
  --image ghcr.io/acme/embeddings:latest --cpu cpu3c --vcpu-count 8
```

`--type queue` creates a [queue-based endpoint](/serverless/endpoints/overview) that runs jobs. `--type load-balancer` creates a [load balancing endpoint](/serverless/load-balancing/overview) that receives HTTP requests directly. A load balancing endpoint needs `--requests-per-worker`. A queue endpoint scales on queue delay, which defaults to 4 seconds.

For GPU workers, pass `--gpu` with a GPU name such as `4090`, `h100`, or `a100-sxm4`, or a Serverless GPU pool ID. Add a count, such as `h100:2`, or set it with `--gpu-count`. Repeat `--gpu` to allow more than one GPU type. For CPU workers, pass `--cpu` with a CPU type such as `cpu3c`, and set the vCPUs with `--vcpu-count` or a suffix such as `cpu3c:8`. To compare hardware first, run [`rp catalog --serverless`](#rp-catalog).

| Flag | Description |
| --- | --- |
| `--name NAME` | The endpoint name. Required. |
| `--type TYPE` | `queue` or `load-balancer`. Required. You can't change it later. |
| `--image IMAGE` | The container image. |
| `--template ID` | A Serverless template ID whose container settings to use. |
| `--gpu TYPE[:COUNT]` | A GPU type or pool ID, and optionally the GPUs per worker. Repeat the flag to allow more than one type. |
| `--gpu-count N` | The number of GPUs per worker. |
| `--cuda VERSION` | The CUDA version for workers. Use `'>=12.4'` for a minimum version, `12.4` or `12.4,12.8` for exact versions, or `any` to remove the constraint. GPU endpoints only. |
| `--cpu TYPE[:VCPUS]` | A CPU type, and optionally the vCPUs per worker. You can't combine it with `--gpu`. |
| `--vcpu-count N` | The number of vCPUs per worker, starting at 2. CPU endpoints only. |
| `--min-workers N` | The minimum number of workers. |
| `--max-workers N` | The maximum number of workers. |
| `--idle-timeout-seconds N` | How long an idle worker waits before it scales down, from 1 to 3600 seconds. |
| `--queue-delay-seconds N` | Add workers when jobs wait in the queue longer than this many seconds. Queue endpoints only. |
| `--requests-per-worker N` | Add workers based on the number of in-flight requests per worker. |
| `--request-timeout-seconds N` | The maximum execution time for a request. |
| `--region REGION` | A region such as `eu`, `na`, or `asia`, or a data center ID prefix such as `us` or `eu-ro`. Repeat the flag to include more than one. |
| `--data-center ID` | An exact data center ID, such as `EU-RO-1`. Repeat the flag to include more than one. |
| `--network-volume ID` | A [network volume](/storage/network-volumes) to attach. Repeat the flag to attach volumes in more than one data center, with at most one per data center. |
| `--global-volume ID` | A [global volume](/storage/globalvolume/overview) to attach. Repeat the flag to attach more than one. |
| `--env KEY=VALUE` | An environment variable. Repeat the flag to set more than one. |
| `--flashboot MODE` | The [FlashBoot](/serverless/endpoints/endpoint-configurations#flashboot) mode: `off`, `standard`, or `priority`. |
| `--disk GB` | The container disk size, in GB. |
| `--port PORT/PROTOCOL` | A port to expose, such as `8000/http`. Repeat the flag to expose more than one. |
| `--args COMMAND` | The container start command, as one string. |
| `--entrypoint COMMAND` | The container `ENTRYPOINT`, as a shell string. |
| `--cmd COMMAND` | The container `CMD`, as a shell string. |
| `--registry NAME` | The name or ID of saved [registry credentials](#secrets-and-registries) for a private image. Pass `''` to clear it. |

Pass one of `--queue-delay-seconds` or `--requests-per-worker`, not both. `--region` expands to every matching data center, and you can combine it with `--data-center`.

### Change an endpoint

You can change an endpoint's configuration in three ways:

- `rp endpoint update` changes the settings you pass as flags. It takes the same flags as `create`, except `--type`.
- `rp endpoint edit` opens the full configuration as JSON in your editor.
- `rp endpoint scale` changes only worker limits and scaling, with `--min-workers`, `--max-workers`, `--idle-timeout-seconds`, `--queue-delay-seconds`, and `--requests-per-worker`.

With `rp endpoint update`, settings you don't pass stay the same. `--env` adds or replaces variables in the existing environment, and `--unset-env KEY` removes one. Flags that take a list, such as `--data-center`, `--region`, `--network-volume`, and `--port`, replace the whole list. You can't switch an endpoint between GPU and CPU workers.

`rp endpoint edit` checks the JSON when you save and close the editor, shows the changes as a patch, and applies them after you confirm. If the JSON isn't valid, the CLI shows the problem and offers to reopen the editor. Fields you remove from the document stay unchanged. To apply a JSON document without an editor, such as in a script, pass `--file PATH`. Use `--file -` to read from stdin, and add `--yes` to skip the confirmation.

Changes to the image or other container settings start a [rolling release](/serverless/endpoints/rolling-releases), and workers move to the new release. `rp endpoint edit` follows the rollout until the new release is live, for up to 10 minutes. Add `--no-follow` to return right away. `rp endpoint update` follows the rollout only when you add `--wait`. Use `--timeout SECONDS` with either command to change how long the CLI follows the rollout. Changes to the name, worker limits, scaling, request timeout, or FlashBoot apply without a new release, so the CLI doesn't wait. If you press Ctrl-C while the CLI follows a rollout, the rollout continues. To check on it later, run `rp endpoint releases ENDPOINT_ID`.

### Monitor workers and logs

`rp endpoint workers` shows how many workers are running, idle, initializing, throttled, or unhealthy, and lists each worker with its status, GPU, data center, release version, and uptime. The list marks workers still on an earlier release as stale. Add `--watch` to refresh the view every 2 seconds until you press Ctrl-C, and `--interval SECONDS` to change the rate. With `--watch --json`, the CLI prints one JSON line per refresh.

`rp endpoint releases` shows the endpoint's current version, rollout progress, and the history of releases with the settings each one changed.

`rp endpoint logs` shows logs from every worker, with each line prefixed by its worker ID. These flags change what it shows:

- `--follow` streams new lines as they arrive and picks up new workers as they start.
- `--worker WORKER_ID` shows only one worker. Repeat the flag to include more than one.
- `--source container` or `--source system` shows only one source.
- `--tail N` sets how many earlier lines to show per worker, up to 5000. The default is 100.
- `--since TIMESTAMP` shows only lines after an RFC 3339 timestamp, such as `2026-10-28T09:00:00Z`.

### Send requests

`rp endpoint run` sends a request to an endpoint. Pass the request body as JSON with `--data`, or from a file with `--input FILE`. Use `--input -` to read from stdin.

For a queue endpoint, the CLI submits a job, waits for it to finish, and prints its output. If the body has no `input` key, the CLI wraps it in one, so `--data '{"prompt": "hello"}'` sends `{"input": {"prompt": "hello"}}`. If the job doesn't complete, for example because it failed or timed out, the command exits with an error.

```bash
rp endpoint run ENDPOINT_ID --input request.json           # Wait for the output
rp endpoint run ENDPOINT_ID --input request.json --stream  # Print streamed output as it arrives
rp endpoint run ENDPOINT_ID --input request.json --async   # Print the job ID and return
```

| Flag | Description |
| --- | --- |
| `--async` | Submit the job and print its ID without waiting. |
| `--stream` | Print output as the handler [streams it](/serverless/workers/handler-functions#streaming-handlers). You can't combine it with `--async`. |
| `--timeout SECONDS` | How long to wait for the result before the CLI stops waiting. The job keeps running. |
| `--webhook URL` | A URL to notify when the job finishes. |
| `--execution-timeout SECONDS` | The maximum time the job can run. |
| `--ttl SECONDS` | How long the job can exist, including time in the queue, before it expires. |
| `--low-priority` | Don't add workers for this job. |

If you press Ctrl-C while the CLI waits, the job keeps running, and the CLI prints the command to resume waiting. To work with a job after you submit it, use `rp endpoint job`:

```bash
rp endpoint job get ENDPOINT_ID JOB_ID      # Show the job's status and output
rp endpoint job wait ENDPOINT_ID JOB_ID     # Wait for the job and print its output
rp endpoint job stream ENDPOINT_ID JOB_ID   # Print the job's streamed output
rp endpoint job cancel ENDPOINT_ID JOB_ID   # Cancel a queued or running job
rp endpoint job retry ENDPOINT_ID JOB_ID    # Requeue a failed or timed-out job
```

`rp endpoint purge` removes every job waiting in an endpoint's queue. Jobs that are already running continue. The CLI asks you to confirm. Add `--yes` to skip the prompt. A non-interactive shell requires `--yes`.

For a load balancing endpoint, the CLI sends an HTTP request to the endpoint's URL and prints the response. Pass the request path with `--path`, which defaults to `/`. The method is POST when you pass a body and GET otherwise. To use another method, pass `--method`. The job flags in the preceding table don't apply.

```bash
rp endpoint run ENDPOINT_ID --path /v1/models
rp endpoint run ENDPOINT_ID --path /v1/chat/completions --input request.json
```

### Delete an endpoint

`rp endpoint delete` deletes an endpoint and its workers. The CLI asks you to confirm. Add `--yes` to skip the prompt. A non-interactive shell requires `--yes`.

## rp catalog

Compare GPU and CPU pricing and stock across data centers before you choose hardware for a Pod or Serverless endpoint:

```bash
rp catalog                                              # All GPUs with Pod pricing and stock
rp catalog h100 --count 2 --region eu --cuda '>=12.4'   # Two H100s in Europe with CUDA 12.4 or later
rp catalog 4090 --serverless                            # Serverless pricing and GPU pool
rp catalog --cpu --vcpu 8 --available                   # In-stock CPU types with 8 vCPUs
rp catalog --datacenters --region us                    # Data centers whose ID starts with US
```

To narrow the results, pass a GPU name such as `4090`, `h100`, or `a100-sxm4`, or a Serverless GPU pool ID. With `--cpu`, pass a CPU type such as `cpu3c` or `cpu5c` instead. Results list the hardware with the most stock first, then the lowest price, and show the stock level in each data center that has the hardware.

By default, the command shows Pod prices for Secure Cloud and Community Cloud. Add `--serverless` to show Serverless prices and the GPU pool for each GPU. The results leave out GPUs that aren't offered on Serverless.

| Flag | Description |
| --- | --- |
| `--serverless` | Show Serverless prices, GPU pools, and stock instead of Pod prices. |
| `--cpu` | Search CPU types instead of GPUs. CPU types are available only in Secure Cloud. |
| `--datacenters` | List data centers with their region, network volume types, global networking support, and compliance certifications. |
| `--count N` | The number of GPUs per Pod or worker. Prices and stock reflect this count. Defaults to 1. |
| `--vcpu N` | The number of vCPUs per Pod or worker. Use with `--cpu`. |
| `--region REGION` | Limit results to a region such as `eu`, `na`, or `asia`, a data center ID prefix such as `us` or `eu-ro`, or a data center ID such as `EU-RO-1`. Repeat the flag to include more than one. |
| `--cloud TIER` | Show only `secure` or `community` Pod prices. Doesn't apply with `--serverless`. |
| `--cuda VERSION` | Filter by CUDA version. Use `'>=12.4'` for a minimum version, or `12.4` or `12.4,12.8` for exact versions. |
| `--min-vram GB` | The minimum VRAM per GPU, in GB. |
| `--max-price USD` | The maximum price per GPU per hour, in US dollars. |
| `--available` | Only show hardware that's in stock. |
| `--json` | Print JSON instead of a table, for use in scripts. |

`--count`, `--cuda`, `--min-vram`, and `--max-price` apply only to GPU searches. With `--datacenters`, filter by passing `--region` or a region as the query. The other filters don't apply.

To use what you find in an app, see [GPU types](/sdk/configuration/gpu-types) and [CPU types](/sdk/configuration/cpu-types).

## rp volume

Create and manage network volumes and global volumes. Commands act on network volumes by default. Add `--global` to act on global volumes instead.

```bash
rp volume list                                          # List network volumes
rp volume list --global                                 # List global volumes
rp volume get VOLUME_ID                                 # Show one volume
rp volume create --name models --size 100 --region eu   # Network volume in a European data center
rp volume create --name shared --global                 # Global volume
rp volume update VOLUME_ID --name new-name              # Rename a volume
rp volume expand VOLUME_ID --size +50                   # Add 50 GB to a network volume
rp volume delete VOLUME_ID                              # Delete a volume and its data
```

If you leave out `VOLUME_ID` from `rp volume get`, the CLI prompts you to pick a volume. Add `--json` to `list`, `get`, `create`, `update`, or `expand` to print JSON for use in scripts.

### Create a network volume

A network volume lives in one data center, so `rp volume create` needs a size and a location. Pass `--size` in GB, from 10 to 4096, and choose the location with one of these flags:

| Flag | Description |
| --- | --- |
| `--data-center ID` | An exact data center ID, such as `EU-RO-1`. |
| `--region REGION` | A region such as `eu` or `na`, a data center ID prefix such as `us` or `eu-ro`, or a data center ID. Repeat the flag to include more than one. |

You can't combine the two flags. If you pass neither, the CLI considers every data center that offers network volumes. When more than one data center matches, the CLI prompts you to pick one. In a non-interactive shell, such as a script or CI job, pass `--data-center` instead.

To choose a storage tier, add `--type standard` or `--type high_performance`. The CLI then picks only from data centers that offer that tier. If you leave out `--type`, the volume uses the data center's primary tier. You can't change the tier after you create the volume. To see which tiers each data center offers, run `rp catalog --datacenters`. See [High-performance storage](/storage/high-performance-storage).

A global volume isn't tied to a data center and grows with your data, so `rp volume create --global` takes only `--name`. See [Global volumes](/storage/globalvolume/overview).

### Resize or rename a volume

Network volumes can grow but can't shrink. `rp volume expand` takes a new total size, such as `--size 200`, or an amount to add, such as `--size +50`. The total can't exceed 4096 GB.

`rp volume update` renames a volume with `--name`, sets a new total size for a network volume with `--size`, or does both. To rename a global volume, add `--global`. Global volumes have no size to change.

### Delete a volume

`rp volume delete` permanently deletes a volume and all the data stored on it. The CLI shows the volume's details and asks you to confirm. Add `--yes` to skip the prompt. A non-interactive shell requires `--yes`. To delete a global volume, add `--global`.

## rp completion

Print a shell completion script for `bash`, `zsh`, or `fish`. Completion covers commands, flags, and resource IDs. To turn it on, add the matching line to your shell profile:

```bash
eval "$(rp completion zsh)"     # ~/.zshrc
eval "$(rp completion bash)"    # ~/.bashrc
rp completion fish | source     # ~/.config/fish/config.fish
```

Open a new terminal for the change to take effect.
