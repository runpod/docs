title: "Batch jobs"
description: "Submit large collections of Serverless inference requests as named batch jobs, then monitor asynchronous processing and retrieve results."
---

Batch jobs let you run large volumes of inference requests against a Serverless endpoint without waiting for each result in real time. Batches run asynchronously on dedicated workers that are separate from your endpoint's standard `/run` traffic, so a large batch never takes capacity from your interactive requests.

## Requirements

- A queue-based Serverless endpoint. To create one, see the [Serverless quickstart](/serverless/quickstart).
- A Runpod [API key](/get-started/credentials#api-keys), if you use the API.

## When to use batch vs /run

| | Batch | `/run` |
|---|---|---|
| **Use case** | Bulk, offline workloads | Interactive, real-time inference |
| **Latency** | Multi-hour | Seconds to minutes |
| **Traffic isolation** | Dedicated batch workers | Standard Serverless workers |
| **Result delivery** | Poll or subscribe to notifications | Synchronous or async poll |

Use batch when your workload can tolerate multi-hour latency. Common examples include:

- Nightly dataset processing.
- Pre-computing embeddings.
- Running evaluations.

Keep using `/run` or `/runsync` for any request a user is waiting on.

<Note>
  Batch requests are billed at a discounted rate compared to on-demand Serverless pricing. There are separate discount tiers for consumer and enterprise GPUs. For discount rates, [contact sales](https://www.runpod.io/contact). To estimate cost, run a small test batch (for example, 100 requests) and extrapolate.
</Note>

## Batch lifecycle

A batch moves through the following API states:

```text
DRAFT → FINALIZED → FAILED
                  → CANCELLED
```

- **DRAFT**: The batch is a draft, and you can still change its requests. Batch workers haven't started any work.
- **FINALIZED**: The batch is locked, and you can't add or remove requests. Batch workers process the requests while the batch stays in this state, and the API has no separate `RUNNING` or `COMPLETED` batch status. Track progress with the `requestTotal`, `requestInProgress`, `requestCompleted`, and `requestFailed` counts. All requests have finished when `requestCompleted + requestFailed` equals `requestTotal`.
- **FAILED**: The batch itself failed before or during execution. This is different from individual request failures in a batch whose other requests finished.
- **CANCELLED**: You cancelled the batch. For details, see [Cancellation](#cancellation).

A batch doesn't start processing until you finalize it. A `DRAFT` batch never runs.

The console shows different status labels. For the mapping, see [Console statuses](#console-statuses).

## API walkthrough

The following steps create a batch, finalize it, check its progress, and read the results. Replace `ENDPOINT_ID`, `API_KEY`, and `BATCH_ID` with your own values.

### Step 1: Create a batch

Create a batch with an initial list of requests:

```bash
curl -X POST https://api.runpod.ai/v2/ENDPOINT_ID/batch \
  -H "Authorization: Bearer API_KEY" \
  -H "Content-Type: application/json" \
  -d '[
    { "input": { "text": "The quick brown fox" } },
    { "input": { "text": "Jumped over the lazy dog" } }
  ]'
```

The request body is a top-level JSON array. Each element uses the same shape as a standard `/run` request: a JSON object with an `input` field. To create an empty batch and add requests later, send an empty array (`[]`).

The response includes the batch ID, which you use in the remaining steps:

```json
{
  "id": "batch_01j9abc123",
  "status": "DRAFT"
}
```

### Step 2: Add more requests (optional)

While the batch is a draft, you can append more requests:

```bash
curl -X POST https://api.runpod.ai/v2/ENDPOINT_ID/batch/BATCH_ID/requests \
  -H "Authorization: Bearer API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "requests": [
      { "input": { "text": "More text to embed" } },
      { "input": { "text": "Another piece of text" } }
    ]
  }'
```

Each call accepts up to 10 MiB. To build a large batch, call this endpoint as many times as you need.

### Step 3: Finalize the batch

Finalize the batch to lock its requests and make it eligible to run:

```bash
curl -X POST https://api.runpod.ai/v2/ENDPOINT_ID/batch/BATCH_ID/finalize \
  -H "Authorization: Bearer API_KEY"
```

The batch status changes to `FINALIZED`. You can no longer add or remove requests.

### Step 4: Check batch progress

Fetch the batch summary to check progress:

```bash
curl https://api.runpod.ai/v2/ENDPOINT_ID/batch/BATCH_ID \
  -H "Authorization: Bearer API_KEY"
```

```json
{
  "id": "batch_01j9abc123",
  "endpointId": "abc123xyz",
  "status": "FINALIZED",
  "requestTotal": 1000,
  "requestInProgress": 8,
  "requestCompleted": 244,
  "requestFailed": 6,
  "createdAt": 1783584000000
}
```

This batch is still processing: 244 of 1,000 requests are complete and 6 have failed. A batch reports `FINALIZED` while it runs. All of its requests have finished when `requestCompleted + requestFailed` equals `requestTotal`. The status only changes again if the batch fails (`FAILED`) or you cancel it (`CANCELLED`). The `createdAt` field is a Unix timestamp in milliseconds.

You can poll the batch summary at whatever interval suits your workflow, or use [notifications](#notifications) instead.

### Step 5: Retrieve results

Fetch the results for every request in the batch:

```bash
curl "https://api.runpod.ai/v2/ENDPOINT_ID/batch/BATCH_ID/requests?offset=0&limit=50" \
  -H "Authorization: Bearer API_KEY"
```

```json
{
  "requests": [
    {
      "id": "req_abc001",
      "status": "COMPLETED",
      "output": { "embedding": [0.12, 0.34, ...] },
      "startedAt": "2026-07-09T09:15:00Z",
      "completedAt": "2026-07-09T09:15:02Z"
    },
    {
      "id": "req_abc002",
      "status": "FAILED",
      "error": "Handler raised an exception: timeout exceeded",
      "startedAt": "2026-07-09T09:15:01Z",
      "completedAt": "2026-07-09T09:15:10Z"
    }
  ],
  "total": 1000,
  "offset": 0,
  "limit": 50,
  "hasMore": true
}
```

Results are paginated. Use the `offset` and `limit` query parameters to page through them. When `hasMore` is `true`, more pages remain.

## API reference

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/v2/ENDPOINT_ID/batch` | Create a batch, optionally with initial requests. |
| `POST` | `/v2/ENDPOINT_ID/batch/BATCH_ID/requests` | Append requests to a draft batch. |
| `POST` | `/v2/ENDPOINT_ID/batch/BATCH_ID/finalize` | Lock the batch and make it eligible to run. |
| `PUT` | `/v2/ENDPOINT_ID/batch/BATCH_ID` | Update batch attributes, such as the display name. |
| `DELETE` | `/v2/ENDPOINT_ID/batch/BATCH_ID/requests/REQUEST_ID` | Remove a single request from a draft batch. |
| `GET` | `/v2/ENDPOINT_ID/batch` | List all batches for an endpoint, newest first. |
| `GET` | `/v2/ENDPOINT_ID/batch/BATCH_ID` | Get the batch summary with request counts. |
| `POST` | `/v2/ENDPOINT_ID/batch/BATCH_ID/cancel` | Cancel a batch. |
| `GET` | `/v2/ENDPOINT_ID/batch/BATCH_ID/requests` | List the batch's requests, paginated. |

## Monitoring batches in the console

To see all batches for an endpoint, open the endpoint in the [Runpod console](https://console.runpod.io/serverless) and select the **Bulk Requests** tab. Each row shows the batch name, status, and progress counts.

To create a batch in the console:

<Steps>
  <Step title="Open the Bulk Requests tab">
    Open your endpoint and select the **Bulk Requests** tab.
  </Step>
  <Step title="Add your requests">
    Click **Create batch**, then enter a JSON request object or an array of request objects. You can edit the requests until you run the batch.
  </Step>
  <Step title="Run the batch">
    Click **Run this batch** to finalize the batch.
  </Step>
</Steps>

Click a batch to open its detail view, which shows:

- The batch's status and progress.
- A row for each request, with its status, timestamps, and an error message if it failed.
- Links to the full detail view for each request.

The request list shows failed requests first, then in-progress, queued, and completed requests.

### Console statuses

The console uses different status labels from the API:

| Console status | API `status` |
| --- | --- |
| **Draft** | `DRAFT` |
| **Running** | `FINALIZED` (requests still processing) |
| **Completed** | `FINALIZED` (all requests finished) |
| **Failed** | `FAILED` |
| **Cancelled** | `CANCELLED` |

## Notifications

When a batch reaches a terminal state (`FAILED` or `CANCELLED`), Runpod sends:

- **Console Inbox notification**: Includes the batch ID, endpoint name, terminal status, and request counts (completed, failed, and total).
- **Webhook event**: Sent if your account has a webhook subscription for batch events.

Each notification is sent once per terminal state. Runpod doesn't send notifications for intermediate progress.

## Cancellation

To cancel a batch:

```bash
curl -X POST https://api.runpod.ai/v2/ENDPOINT_ID/batch/BATCH_ID/cancel \
  -H "Authorization: Bearer API_KEY"
```

When you cancel a batch:

- Queued requests are cancelled immediately and aren't billed.
- In-progress requests finish and are billed normally.

The batch status changes to `CANCELLED` once all in-progress requests have finished.

| Limit | Value |
|-------|-------|
| Active batches per endpoint | 10 |
| Requests per batch | 5,000 |
| Queued requests per endpoint | 50,000 |

<Note>Limits can be raised up to 3,000,000 requests per day. Contact support or sales for higher limits.</Note>

## Billing

Batch requests are billed at a discounted rate compared to on-demand Serverless pricing, with separate discount tiers for consumer and enterprise GPUs. For discount rates, [contact sales](https://www.runpod.io/contact).

Billing is based on the compute time each request uses. If you cancel a batch, requests that were already in progress are still billed. For general Serverless pricing, see [Pricing](/serverless/pricing).

## Error handling

A failed request doesn't fail the batch. The batch stays `FINALIZED` and keeps processing the remaining requests. To inspect failed requests, use the console or the `GET .../requests` endpoint. Each failed request includes the error message from your handler.

If the batch itself has the `FAILED` status, the problem is systemic rather than an error in individual requests. Check the request-level errors first, and contact support if they don't explain the failure.

Batch requests use the same queue as standard Serverless requests. If the queue fails, queued batch requests may be lost. This also applies to `/run` traffic.

## Known limitations

- Batches use the GPU type configured on your endpoint. You can't choose a different GPU per batch or per request.
- Requests within a batch run in no particular order, and you can't schedule individual requests.
- Runpod doesn't show a cost estimate before you finalize a batch. To estimate cost, run a small test batch and extrapolate.
- Runpod schedules batch workers based on global queue urgency and off-peak capacity, so start times aren't guaranteed. Runpod attempts to run each batch within 24 hours on a best-effort basis.
