The [Runpod Terraform provider](https://registry.terraform.io/providers/runpod/runpod/latest) lets you manage Runpod infrastructure as code. You declare Pods, Serverless endpoints, templates, network volumes, and registry credentials in HCL files, and Terraform creates, updates, and removes them to match.

This page covers the 2.0.0 provider. If you already manage Runpod resources with a 1.x version of the provider, read [Migrate the Runpod Terraform provider from 1.x to 2.0.0](/integrations/terraform/migration) before you upgrade, because 2.0.0 is a breaking release.

## Requirements

- [Terraform](https://developer.hashicorp.com/terraform/install) 1.6 or later.
- A Runpod account with a [Runpod API key](/get-started/credentials).

## Install the provider

Create a directory for your configuration and add a `main.tf` file that declares the Runpod provider:

```hcl main.tf
terraform {
  required_version = ">= 1.6"

  required_providers {
    runpod = {
      source  = "runpod/runpod"
      version = "~> 2.0"
    }
  }
}

provider "runpod" {}
```

The `~> 2.0` constraint accepts any 2.x release and blocks an automatic move to a future 3.0 major version. To pin one exact release instead, set `version = "2.0.0"`.

Download the provider into your working directory:

```bash
terraform init
```

Terraform records the selected provider version in `.terraform.lock.hcl`. Commit that file so everyone on your team uses the same version. To move to a newer release within your constraint, run `terraform init -upgrade`.

## Authenticate

The provider needs a Runpod API key. It reads the key from the `api_key` argument first, then falls back to the `RUNPOD_API_KEY` environment variable. If neither is set, Terraform stops with an error when it configures the provider.

### Use an environment variable

Setting the key as an environment variable keeps it out of your configuration files and state. This is the recommended method:

```bash
export RUNPOD_API_KEY="YOUR_API_KEY"
```

With the variable set, leave the provider block empty: `provider "runpod" {}`.

### Use a provider argument

To pass the key through Terraform instead, declare a sensitive variable and reference it in the provider block:

```hcl main.tf
variable "runpod_api_key" {
  type      = string
  sensitive = true
}

provider "runpod" {
  api_key = var.runpod_api_key
}
```

Supply the value at run time, for example with `terraform apply -var="runpod_api_key=YOUR_API_KEY"` or a `TF_VAR_runpod_api_key` environment variable. Never commit the key to a `.tfvars` file in version control.

<Note>
  The provider sends requests to the production Runpod API by default. To target a different host, set the `base_url` argument or the `RUNPOD_API_BASE_URL` environment variable. Most users never need this setting.
</Note>

## Deploy a Pod

This example creates a single GPU Pod running PyTorch and outputs its ID and status.

<Steps>
  <Step title="Add the Pod to your configuration">
    Add the following resource and outputs to `main.tf`, below the provider block:

    ```hcl main.tf
    resource "runpod_pod" "example" {
      name        = "terraform-example"
      image       = "runpod/pytorch:2.8.0-py3.11-cuda12.8.1-cudnn-devel-ubuntu22.04"
      gpu_type_id = "NVIDIA GeForce RTX 4090"
      gpu_count   = 1
      cloud       = "SECURE"
      disk        = 20
      ports       = ["8888/http", "22/tcp"]
    
      env = {
        JUPYTER_PASSWORD = "CHANGE_ME"
      }
    }
    
    output "pod_id" {
      value = runpod_pod.example.id
    }
    
    output "pod_status" {
      value = runpod_pod.example.status
    }
    ```

    `name`, `image`, and a GPU or CPU type are the minimum a Pod needs. `ports` is a list of `PORT/PROTOCOL` strings, and `env` is a map of environment variables.
  </Step>
  <Step title="Review the plan">
    Preview what Terraform will create:

    ```bash
    terraform plan
    ```

    The plan should show one `runpod_pod` to add and nothing to change or destroy.
  </Step>
  <Step title="Apply the configuration">
    Create the Pod:

    ```bash
    terraform apply
    ```

    Type `yes` when prompted. When the apply finishes, Terraform prints the `pod_id` and `pod_status` outputs. The Pod also appears on the [Pods page](https://www.runpod.io/console/pods) of the Runpod console.
  </Step>
  <Step title="Clean up">
    When you're done, remove the Pod so it stops billing:

    ```bash
    terraform destroy
    ```
  </Step>
</Steps>

<Warning>
  A running Pod bills for every minute it exists, whether or not you use it. Run `terraform destroy` when you finish testing, or set `desired_state = "EXITED"` on the Pod to stop it while keeping it in your configuration.
</Warning>

## What the provider manages

The 2.0.0 provider covers these resources:

- Pods, including CPU Pods, with `runpod_pod`, and one-off Pod actions such as a restart with `runpod_pod_action`.
- Serverless endpoints with `runpod_serverless_endpoint`.
- Templates with `runpod_template`.
- Network volumes with `runpod_network_volume`.
- Container registry credentials and Amazon ECR delegations with `runpod_registry` and `runpod_registry_delegation`.
- Instant Clusters with `runpod_cluster`.
- Account SSH keys with `runpod_account_ssh_keys`.

Data sources read the GPU, CPU, and data center catalogs, existing Pods and templates, endpoint workers, builds, releases, logs, and billing. For every argument and attribute, see the [provider reference on the Terraform Registry](https://registry.terraform.io/providers/runpod/runpod/latest/docs). The reference is generated from the provider schema, so it always matches the release you install.

## Which Runpod APIs the provider uses

The 2.0.0 provider is generated from the [Runpod REST API v2](/api-reference-v2/overview), and nearly every resource and data source talks only to `https://api.runpod.io/v2`.

A small set of reads still reaches older APIs because v2 does not yet expose the route:

- The account identity lookup.
- The three 1.x billing data sources.
- A few Pod, endpoint, and template read-backs, which use REST API v1.
- The container registry username on `runpod_registries`, which uses the GraphQL API.

Each of these is deprecated. Terraform prints a deprecation warning on every plan that touches one, and each is removed once the v2 API adds the matching route. The provider's `graphql_url` argument, with its `RUNPOD_GRAPHQL_URL` fallback, applies only to the GraphQL call, so leave it unset unless you work against a non-production environment.
