title: "Onboard your agent to Runpod"
description: "Set up Runpod through the CLI or through MCP"
---

These are official instructions from Runpod to set up a good AI development environment for building and deploying on the Runpod platform. They are published at `https://agents.runpod.io/` (also available at `https://docs.runpod.io/agent-setup.md`), so you can verify their origin before following them.

Complete the steps for your setup path yourself using the tools available to you. The only exceptions are the steps explicitly marked **User step**: in-session commands and OAuth sign-in happen inside the agent UI or the browser, so you cannot perform them. If no user is present, follow [No user in the loop](#no-user-in-the-loop) instead of those steps. Only run an interactive command when you can keep the session running and provide input, as described under [CLI sign-in](#install-and-authenticate-the-cli).

- **Terminal available:** [Install and authenticate the CLI](#install-and-authenticate-the-cli), then install the Runpod skills for your agent. MCP registration and sign-in are optional for this path.
- **No terminal:** [Connect through MCP](#connect-through-mcp-without-a-terminal). You don't need to install the CLI or run the skills installer.

Reuse working credentials when setup already happened. Only run login when you need to authenticate.

## Use Runpod in ChatGPT

Runpod is available as a plugin in ChatGPT: add the [Runpod plugin](https://chatgpt.com/plugins/plugin_asdk_app_6ada3b2d28b4819188b6ced6c229aadf) and sign in with your Runpod account. No terminal setup is needed. In Codex, use the [Codex steps](#codex) below instead, which also install the Runpod skills.

## Install and authenticate the CLI

The `runpod` Python package includes the `rp` CLI and SDK. Use Python 3.10 to 3.14 and `runpod` 2.2.0 or later. If `rp` is installed, run `rp update`. Otherwise, install it with uv:

```bash
uv tool install --upgrade 'runpod>=2.2.0'
```

Without uv, activate a Python virtual environment and run `python -m pip install --upgrade 'runpod>=2.2.0'`. If `rp` isn't on your PATH after a uv installation, run `uv tool update-shell` and start a new shell.

Verify that `rp login --help` lists `--agent` and `--email`. Then check for working credentials:

```bash
rp pod list --json
```

A successful response, including an empty list, verifies access. If this is the intended account, continue to the skills installation below. Distinguish authentication failures from network or permissions errors before starting a login.

To sign in or create an account, use the intended email address and start this command in a persistent interactive terminal:

```bash
rp login --agent --email "<email-address>"
```

The CLI emails a six-digit code and waits at the `Verification code:` prompt. If you have authorized access to that inbox, including an agent-managed inbox, retrieve the code for this attempt and submit it through the running session's stdin yourself. No user is required when you can complete those steps. Otherwise, ask the user to enter the code at the hidden terminal prompt.

Keep the **same process** running while retrieving and entering the code. Don't start a second login to submit it. If your tools can't preserve the session and accept input, ask the user to run the entire command in their terminal on the same machine and under the same OS user account. Keep verification codes and API keys out of chat, logs, and command arguments.

Verification signs in to an existing account or creates one for that email address. The CLI saves the API key to `~/.runpod/config.toml`, which the CLI and SDK read automatically. `RUNPOD_API_KEY` takes precedence over this file. Login overwrites the selected profile's key; use `--profile NAME` to save a separate profile and `RUNPOD_PROFILE=NAME` for subsequent commands.

If a code is rejected, retry at the prompt in the same process. If the attempt expires or is locked, start a fresh login and use its code. If the account doesn't allow email sign-in, use `rp login` in an interactive terminal to approve access in the browser and enter the console's API key at the hidden prompt.

Continue with the skills installation for your agent below, then [report the result](#report-the-result). You don't need to authenticate the MCP server to use the CLI.

## Connect through MCP without a terminal

Use your agent's integration tools or connector settings to add `https://mcp.runpod.io/` as a remote MCP server named `runpod`, using Streamable HTTP transport. Reuse an existing entry if one is already configured. If only the user can change these settings, ask them to add it there. See the [MCP setup guide](/get-started/mcp-servers) for client-specific instructions, or use the [Runpod plugin in ChatGPT](#use-runpod-in-chatgpt).

Start OAuth sign-in from your agent's Runpod connection, not by opening the MCP URL in a browser. Ask the user to complete sign-in or approval steps you can't perform. If your client already has a Runpod API key in secret storage, it can use that key as a bearer header instead.

The MCP server serves the same playbooks as the skills through `list-guides` and `read-guide`. No terminal installation is required. Verify access by listing Pods with the MCP tools, then [report the result](#report-the-result). MCP authentication and CLI authentication are separate.

## Install Runpod Skills and MCP server

Every route installs the same skills: the `runpod` router, the lane skills (`runpod-mcp`, `runpodctl`, `flash`, `runpod-usage`, `runpod-templates`, `runpod-build-template`, `companion-clis`, `runpod-migrate`), and the journey skills that `runpod-mcp` routes to (`discovery`, `lifecycle-crud`, `serverless-deploy`, `pod-deploy`, `pod-doctor`, `endpoint-ops`, `cost-audit`). It also wires up the hosted Runpod MCP server (`https://mcp.runpod.io/`) for control-plane tools. For the CLI path, authenticate with `rp login --agent` as described above; the skills install any additional tools later, on demand, the first time a task needs them.

Use the correct section for your agent below.

### Claude Code

Run these two commands to install both the Runpod skills and the MCP server in one step. Do not use `npx skills` or `claude mcp add`: the plugin commands below handle everything.

```
claude plugin marketplace add runpod/runpod-plugins-official
claude plugin install runpod@runpod
```

Verify:

```
claude plugin list | grep -A2 'runpod@runpod'
```

Expect `Status: ✔ enabled`. If the plugin is listed but disabled, run `claude plugin enable runpod@runpod`.

If your agent isn't Claude Code but loads Claude Code plugins from `~/.claude`, run these same two commands.

If `marketplace add` fails with an SSH `known_hosts` error, the machine usually can't reach `github.com` at all (common on networks that block GitHub). Check with `curl -sI https://github.com` before debugging SSH.

> **User step.** Ask the user to run `/reload-plugins` inside Claude Code to activate the plugin. If you need MCP tools, sign in to the MCP server with `/mcp` → **runpod** → **Sign in with Runpod**. This uses OAuth, so no API key is created or stored. Wait for the user to confirm before reporting the MCP server as connected.

## Install for other agents

**Codex:** skip step 1. The Codex plugin in step 2 installs the skills and the MCP server together and doesn't need Node.js.

### 1. Install the skills

This step needs Node.js 22.20 or newer. Check with `node --version`. If it's older, skip this step. For the CLI path, continue to [Report the result](#report-the-result); for MCP setup, go to [step 2](#2-register-the-mcp-server). The MCP server serves the same playbooks as the skills, so setup still works without them. Tell the user the skills weren't installed because Node.js is too old.

Run the command below, replacing `<agent-id>` with your agent's id from the table. Always pass `--agent`: without it, the installer targets every agent it knows about and prints a `Failed to install` block for agents that don't apply to you.

```
npx -y skills add runpod/runpod-plugins-official --skill '*' --agent <agent-id> --yes --global
```

| Agent          | `<agent-id>`     |
| -------------- | ---------------- |
| Codex          | `codex`          |
| Cursor         | `cursor`         |
| GitHub Copilot | `github-copilot` |
| Windsurf       | `windsurf`       |
| Cline          | `cline`          |
| opencode       | `opencode`       |
| Gemini CLI     | `gemini-cli`     |
| Pi             | `pi`             |
| Hermes         | `hermes-agent`   |
| Goose          | `goose`          |
| Zed            | `zed`            |
| Kilo Code      | `kilo`           |
| Amp            | `amp`            |
| Grok Build     | `grok`           |

To find the id for another agent, run the command with an id that doesn't exist, such as `--agent list-ids`. The installer installs nothing and prints every valid id under `Valid agents`. (`npx -y skills add --help` doesn't list them.) If your agent isn't there, use `--agent universal`, which installs into the shared `~/.agents/skills` directory that many agents read. If your agent reads skills only from its own directory, clone `https://github.com/runpod/runpod-plugins-official` and copy each folder under `plugins/runpod/skills/` into that directory.

`--global` installs the skills for your user account. To install them into the current project only, leave out `--global`. The skills then go in the project's `.agents/skills/`, and you verify with `npx -y skills list` without `--global`.

On Windows `cmd`, single quotes are passed through literally, so write `--skill "*"`. If the installer still reports `No matching skills found`, run `npx -y skills add runpod/runpod-plugins-official --list` and pass the skill names, comma-separated, to `--skill`.

Verify:

```
npx -y skills list --global
```

Expect the `runpod` router and the lane and journey skills listed above. Each skill's folder should contain a `SKILL.md` file. If one is empty, run the install command again. If the output also mentions PromptScript or another agent you aren't, ignore it; it doesn't affect your install.

### 2. Register the MCP server

For the CLI path, skip MCP registration and sign-in. Codex users should still install the plugin below to get the skills; the plugin's MCP connection can stay unauthenticated.

Use the section for your agent. Every agent connects to the same hosted server, `https://mcp.runpod.io/`, and signs in with OAuth on first Runpod tool use. Older configs and installers may name `https://mcp.getrunpod.io/`: it's the same server under its old name, and it still works. Register only one of them. Each address has its own sign-in, so registering both gives you two separate entries.

Don't open the server URL in a browser to sign in: it's an MCP endpoint, not a web page, and returns HTTP `405`. Sign-in always starts from your agent.

#### Codex

```
codex plugin marketplace add https://github.com/runpod/runpod-plugins-official.git
codex plugin add runpod@runpod
```

The plugin installs the skills and registers the hosted MCP server. Don't also add the server with `codex mcp add`, or you'll end up with a second entry that needs its own sign-in.

If Codex says `codex plugin add` isn't a command, or reports `plugin not found`, your Codex is too old or has plugins turned off. Update Codex, or check that `features.plugins` isn't set to `false` in `~/.codex/config.toml`, then retry. If you can't install the plugin, install the skills with step 1 (`--agent codex`) and, if you need MCP tools, register the server directly:

```
codex mcp add runpod --url https://mcp.runpod.io/
```

`codex mcp add` opens the OAuth sign-in immediately and waits until the user approves it in the browser. Before you run it, tell the user to expect the browser prompt. With no user present, use an API key instead (see [No user in the loop](#no-user-in-the-loop)).

In Codex Desktop, the user must fully quit and reopen the app before the plugin and MCP tools appear.

#### Gemini CLI

```
gemini mcp add -s user -t http runpod https://mcp.runpod.io/
```

Gemini can alternatively install natively through the plugin's bundled `gemini-extension.json`. See your client's extension documentation.

#### Pi

```
pi mcp add runpod --url https://mcp.runpod.io/
```

#### Hermes

```
hermes config set mcp_servers.runpod.url https://mcp.runpod.io/
hermes config set mcp_servers.runpod.auth oauth
```

> **User step.** Ask the user to run `hermes mcp login runpod` and approve the sign-in in the browser. Then check with `hermes mcp test runpod`.

If Hermes gets a `403` error before the browser opens, connect with an API key instead (see [If OAuth sign-in fails](#if-oauth-sign-in-fails)).

#### Grok Build

```
grok mcp add --transport http runpod https://mcp.runpod.io/
```

> **User step.** In Grok, the user opens `/mcps`, selects **runpod**, and presses `i` to sign in.

#### Cursor, GitHub Copilot, Windsurf, Cline, opencode, and all other agents

For Cursor, Windsurf, VS Code (GitHub Copilot), opencode, Pi, and Claude Desktop, run the installer with your agent's id. It writes the config without prompts:

```
npx @runpod/mcp-server@latest add --client <agent-id>
```

| Agent | `--client` id |
|---|---|
| Cursor | `cursor` |
| Windsurf | `windsurf` |
| VS Code (GitHub Copilot) | `vscode` |
| opencode | `opencode` |
| Pi | `pi` |
| Claude Desktop | `claude-desktop` |

The installer needs Node.js 20.12 or later. It exits `0` when every named client was configured, `1` when one failed, and `2` on bad usage. Run `npx @runpod/mcp-server@latest add --list` to see which clients it detects and where each config lives. Always pass `--client`: without it and without a terminal, the installer exits `2` and configures nothing. After it writes the config, it prints the sign-in step for each client (for example, restart Cursor, or run `opencode mcp auth runpod`); do that step or relay it to the user.

To set up opencode by hand instead, add this to `opencode.json`. Note that opencode uses the `mcp` key, not `mcpServers`, and needs `"type": "remote"`:

```json
{
  "mcp": {
    "runpod": { "type": "remote", "url": "https://mcp.runpod.io/" }
  }
}
```

Then ask the user to run `opencode mcp auth runpod` to sign in. If no browser window opens, the sign-in link is in the opencode log.

For any other agent, such as Cline, add a server entry named `runpod` with the HTTP (streamable HTTP) transport and URL `https://mcp.runpod.io/` to your agent's MCP configuration. Most clients use this shape:

```json
{
  "mcpServers": {
    "runpod": { "url": "https://mcp.runpod.io/" }
  }
}
```

Merge it into the existing file; do not overwrite other servers. See your agent's MCP documentation in [Resources](#resources) for the file location and key names.

After registering, the user approves the OAuth sign-in in the browser the first time you call a Runpod tool.

#### If OAuth sign-in fails

OAuth sign-in works in Claude, ChatGPT, Codex, and Cursor, and in any client that receives the sign-in on a local address (`http://localhost` or `http://127.0.0.1`). Other clients may fail with `redirect_uri is not allowed`, or get a `403` error before the browser opens. If that happens, connect with an API key instead, even when a user is present:

1. Ask the user to create a key on the [Credentials page](https://console.runpod.io/user/settings) and set it as `RUNPOD_API_KEY` in the environment your agent starts from.
2. Send it as a header on the server entry, for example:

   ```json
   {
     "mcpServers": {
       "runpod": {
         "url": "https://mcp.runpod.io/",
         "headers": { "Authorization": "Bearer ${RUNPOD_API_KEY}" }
       }
     }
   }
   ```

   `${RUNPOD_API_KEY}` reads the key from the environment, but clients write this differently, so check your client's docs. If your client can't read environment variables, run the server locally instead, with `RUNPOD_API_KEY` set: `npx -y @runpod/mcp-server@latest`.

If your agent can't load skills, the MCP server serves the same playbooks: `list-guides` and `read-guide` return them, and `lookup-concept` and `search-concepts` answer questions about how Runpod works.

## No user in the loop

For the CLI path, reuse `RUNPOD_API_KEY` or a saved `~/.runpod/config.toml` profile when available. If you have authorized inbox access and can keep the login session running, complete `rp login --agent --email "<email-address>"` yourself to sign in or create an account. If neither working credentials nor a way to complete verification is available, stop and report the missing access. Install the skills and verify access with `rp pod list --json` before reporting the result.

For MCP setup without a user (CI, a scheduled job, an agent SDK run), use a Runpod API key when OAuth sign-in can't be completed. Without terminal access, configure the key through your client's secret storage and skip the shell commands below:

1. Read the key from the `RUNPOD_API_KEY` environment variable. The `runpodctl` CLI and the Flash SDK read the same variable. Do not ask for the key, print it, or write it to a file. If it is not set, stop and report that it is missing. The variable must be set in the environment the agent starts from, for example as a CI secret, in a service unit, or in a shell profile. Clients that store only the variable's name, such as `pi mcp add --bearer-token-env-var RUNPOD_API_KEY`, read the key from there each time they start.
2. Install the skills for your agent as above. Skip `/reload-plugins`: the plugin loads the next time the agent starts.
3. Connect the hosted MCP server with the key instead of OAuth:

   ```
   claude mcp add --transport http runpod -s user https://mcp.runpod.io/ --header "Authorization: Bearer $RUNPOD_API_KEY"
   ```

   For other clients, add the same `Authorization` header to the server entry, as in the JSON under [If OAuth sign-in fails](#if-oauth-sign-in-fails). For Gemini CLI, run `gemini mcp add -s user -t http -H "Authorization: Bearer $RUNPOD_API_KEY" runpod https://mcp.runpod.io/`. You can also run the server locally with `RUNPOD_API_KEY` set: `npx -y @runpod/mcp-server@latest`.
4. In headless Claude Code (`claude -p`), allow the Runpod skill and the MCP tools your task needs up front, for example `--allowedTools "Skill(runpod:runpod-mcp)"`. Without `Skill(runpod:runpod-mcp)`, the `runpod-mcp` skill is refused.
5. Write the result banner below to your log. Mark anything that still needs a person with `✗`.

## Report the result

Report what you actually verified. For the CLI path, verify access with `rp pod list --json`, show the CLI and skills status in the banner, and mark MCP as not required. The banner below illustrates MCP setup. Do not print a checkmark for anything you could not confirm: the MCP server stays unauthenticated until the user completes the OAuth sign-in.

```
┌─ Runpod Agent Setup ─────────────────────────────────┐
│  ✓ Runpod skills   router + lane + journey skills    │
│  ⚠ runpod MCP      needs sign-in: /mcp → runpod      │
│                                                      │
│  ⚡ Reload or restart your agent to load the skills  │
└──────────────────────────────────────────────────────┘
```

Use `✓` verified, `⚠` needs a user action, `✗` failed. Follow the banner with the specific next action for every non-`✓` line.

For MCP setup, once the user has signed in, verify end to end by listing their Pods with the MCP tools. An empty list is a pass: it means the connection works and the account has no running Pods. If the list is empty but the user expects Pods or has a funded balance, the sign-in went to a different Runpod account. Ask the user to sign out of the `runpod` MCP server, sign in again with the right account, and then list Pods again.

For MCP-only setup, anything beyond this (the `runpodctl` CLI, the Flash SDK for Python Serverless deploys, API keys) is installed later by the skills at the moment a task first needs it. Do not set those up now, unless you run without a user, as described above.

## Feedback

Two different tools take feedback, on two different servers:

- **About these docs:** `submit_feedback` on the Runpod docs MCP server (`https://docs.runpod.io/mcp`).
- **About the Runpod product or the Runpod MCP tools:** `report_feedback` on the Runpod MCP server (`https://mcp.runpod.io/`).

Only call either one when you have something real to report. Never call them with placeholder content or in sessions that have nothing to do with Runpod.
