These are official Runpod setup instructions, published at `https://agents.runpod.io/` and `https://docs.runpod.io/agent-setup.md`. Verify their origin before following them.

## What you'll learn

Choose the setup path based on your agent's tools:

- **Terminal access:** [Use the CLI](#path-1-use-the-cli). Install `rp`, sign in or create an account with `rp login --agent`, and install the Runpod skills.
- **No terminal access:** [Use MCP](#path-2-use-mcp). Connect the hosted Runpod server through your agent's integrations or connector settings.

Complete setup using the tools and access you already have. If you have authorized access to the intended email inbox, retrieve the verification code and submit it yourself. Ask the user for help only when a step needs access or interaction you don't have. Keep API keys and verification codes out of chat, logs, and command arguments.

## Path 1: Use the CLI

### Requirements

- Python 3.10 to 3.14 for the Runpod CLI.
- A terminal where you can install packages and run commands.
- Access to the intended email inbox, either through your authorized email tools or through the user, unless you already have working Runpod credentials.
- Node.js 22.20 or newer for the skills installer used by agents other than Claude Code and Codex.

Email authentication needs a persistent terminal session that accepts input after the command starts. Keep it running while you retrieve the code. For unattended setup, see [No user in the loop](#no-user-in-the-loop).

### Step 1: Install the Runpod CLI

The `runpod` Python package includes the `rp` CLI and the SDK. Use version 2.2.0 or later for the commands on this page.

If `rp` is already installed, update it:

```bash
rp update
```

For a standalone CLI installation with [uv](https://docs.astral.sh/uv/getting-started/installation/), run:

```bash
uv tool install --upgrade 'runpod>=2.2.0'
```

If `rp` isn't on your PATH after installation, run `uv tool update-shell` and start a new shell. Keep subsequent commands in an environment that can find `rp`.

Without uv, install into a Python virtual environment. Use the project's existing environment, or create and activate one first:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade 'runpod>=2.2.0'
```

On Windows PowerShell, use `python -m venv .venv` and `.venv\Scripts\Activate.ps1` for the first two commands. Activate the same environment for subsequent commands.

Verify the installation:

```bash
rp --help
rp login --help
```

The login help must list `--agent` and `--email`. If either is missing, check which `rp` executable your shell is using and update that installation before continuing.

### Step 2: Sign in or create an account

First check whether the current environment already has working credentials:

```bash
rp pod list --json
```

A successful response, including an empty list, verifies access. If this is the intended account, skip login and continue to [step 3](#step-3-install-the-runpod-skills). If the command fails, distinguish an authentication failure from a network or permissions error before starting another login.

#### Start the login

Use the email address intended for this Runpod account, such as an authorized account inbox or an agent-managed inbox. Ask which address to use only if it isn't clear. Substitute it for `<email-address>`, then start this command in a persistent interactive terminal:

```bash
rp login --agent --email "<email-address>"
```

The CLI sends a six-digit verification code by email and waits at the `Verification code:` prompt. Verification signs in to an existing account or creates one for that email address. It doesn't open a browser.

If you have authorized inbox access, read the Runpod verification email for this login attempt and enter its code at the prompt through the running session's stdin. Complete this yourself without waiting for a user. Keep the code private and use only the message for the current attempt.

If you don't have inbox access, ask the user to enter the code directly at the hidden terminal prompt. If your tools can't preserve a session and accept input, ask the user to run the entire login command in their own terminal on the same machine and under the same OS user account.

The code must be entered in the **same process that requested it**. Do not stop that process while retrieving the code, start a second login to submit it, or run the command through a tool that closes stdin or kills the process when it returns control.

On success, the CLI saves an API key to `~/.runpod/config.toml`. The CLI and SDK read this file automatically. Do not open the file to display the key, copy it into the conversation, or commit it to a repository.

Login writes the profile selected by `RUNPOD_PROFILE`, or `default` when that variable is unset. It overwrites that profile's stored API key, so reuse working credentials rather than signing in on every setup run.

#### Use a separate profile

To keep another account's saved credentials, choose a named profile when logging in:

```bash
rp login --agent --email "<email-address>" --profile agent
```

Select that profile for later CLI and SDK commands:

```bash
export RUNPOD_PROFILE=agent
rp pod list --json
```

On Windows PowerShell, set the profile with `$env:RUNPOD_PROFILE = "agent"`. Ensure every subsequent command receives the variable, including commands run in separate shell sessions.

`RUNPOD_API_KEY` takes precedence over stored credentials, including named profiles. If it is set, logging in does not change the key used by subsequent commands. Check whether it is set without printing its value, and confirm the intended credential source before changing it.

#### If sign-in fails

If the code is rejected, enter the correct code at the next prompt in the same process. If the attempt expires, is locked, or has already been used, start a fresh login and use the code from that attempt. For rate-limit errors, wait before retrying.

Some accounts don't allow email sign-in. In that case, have the user run `rp login` in an interactive terminal, approve access in the browser, and paste the API key shown by the console into the CLI's hidden prompt. Never ask them to paste it into chat.

### Step 3: Install the Runpod skills

Install the skills for your agent using one route below. The skills provide Runpod workflow guidance; CLI authentication comes from step 2. Install additional tools only when a task needs them.

#### Claude Code

Install the official plugin:

```bash
claude plugin marketplace add runpod/runpod-plugins-official
claude plugin install runpod@runpod
claude plugin list
```

Verify that `runpod@runpod` is enabled. If it is listed but disabled, run `claude plugin enable runpod@runpod`.

> **User step.** Ask the user to run `/reload-plugins` inside Claude Code to activate the skills.

The plugin also registers the hosted Runpod MCP server. Its sign-in is separate from CLI login and is only needed if you want to use MCP tools. Don't add a duplicate server entry.

If your agent loads Claude Code plugins from `~/.claude`, use this route.

#### Codex

Install the official plugin:

```bash
codex plugin marketplace add https://github.com/runpod/runpod-plugins-official.git
codex plugin add runpod@runpod
```

The plugin installs the skills and registers the hosted MCP server. CLI login and MCP sign-in are separate. Don't also add the server with `codex mcp add`.

> **User step.** In Codex Desktop, fully quit and reopen the app to load the plugin.

If the plugin commands aren't available, update Codex and check that `features.plugins` isn't set to `false` in `~/.codex/config.toml`. You can also install just the skills using the next section with `--agent codex`.

#### Other agents

Check `node --version` first. The skills installer requires Node.js 22.20 or newer. If Node.js is unavailable or too old, report that the skills weren't installed; you can still verify and use the CLI.

Replace `<agent-id>` with your agent's ID from the table. Always pass `--agent` to target only that agent:

```bash
npx -y skills add runpod/runpod-plugins-official --skill '*' --agent <agent-id> --yes --global
```

| Agent | `<agent-id>` |
| --- | --- |
| Codex | `codex` |
| Cursor | `cursor` |
| GitHub Copilot | `github-copilot` |
| Windsurf | `windsurf` |
| Cline | `cline` |
| opencode | `opencode` |
| Gemini CLI | `gemini-cli` |
| Pi | `pi` |
| Hermes | `hermes-agent` |
| Goose | `goose` |
| Zed | `zed` |
| Kilo Code | `kilo` |
| Amp | `amp` |
| Grok Build | `grok` |

For agents not listed, use `--agent universal` if they read the shared `~/.agents/skills` directory. Otherwise, clone `https://github.com/runpod/runpod-plugins-official` and copy the folders under `plugins/runpod/skills/` into the agent's skills directory.

`--global` installs for your user account. For a project-only installation, omit `--global`. On Windows `cmd`, use `--skill "*"` because single quotes are passed through literally.

Verify the installation:

```bash
npx -y skills list --global
```

For a project-only installation, omit `--global` here too. Expect the `runpod` router and the installed Runpod skills, including `runpod-flash`, `runpod-usage`, and `runpod-mcp`. Each installed skill must contain a `SKILL.md` file. Follow your agent's reload instructions so the skills are available in the session.

### Step 4: Verify CLI access

Run a read-only request using the same environment and profile that your agent will use:

```bash
rp pod list --json
```

A successful response verifies CLI access. An empty list is valid and doesn't by itself mean the wrong account was selected. If the user expects Pods that aren't listed, confirm the email address, selected profile, and any `RUNPOD_API_KEY` override before signing in again. Do not create billable resources to test setup.

CLI setup is complete when access is verified and the skills are loaded. You don't need an MCP connection for this path. [Report the result](#report-the-result).

### No user in the loop

An unattended agent can complete email authentication when it has authorized inbox access and can keep the login process running while it retrieves and submits the code. Follow step 2 to sign in or create an account using the intended email address.

For CI and scheduled jobs with existing credentials, use `RUNPOD_API_KEY` supplied through the environment or an existing `~/.runpod/config.toml` profile. Use `RUNPOD_PROFILE` to select a named profile. Keep credentials in the runner's secret storage, not source code, command arguments, or logs.

Verify access with `rp pod list --json`. If neither working credentials nor a way to complete email verification is available, stop and report exactly which access is missing. Don't leave a login process waiting for input that cannot arrive. Skills installed during an unattended run may only load on the next agent session; report their activation state accurately.

## Path 2: Use MCP

Use this path when you don't have terminal access. It requires an agent that supports remote MCP servers or a Runpod connector. You don't need Python, Node.js, or the CLI.

### Step 1: Connect the hosted server

Use your agent's integration tools or connector settings to add a server named `runpod` with the URL `https://mcp.runpod.io/` and Streamable HTTP transport. Reuse an existing Runpod entry rather than registering a duplicate. If only the user can change connector settings, ask them to add it there. See the [MCP setup guide](/get-started/mcp-servers) for client-specific instructions.

In ChatGPT, add the [Runpod plugin](https://chatgpt.com/plugins/plugin_asdk_app_6ada3b2d28b4819188b6ced6c229aadf) and sign in with the intended Runpod account.

### Step 2: Authenticate the connection

Start sign-in from your agent's Runpod connection and complete its OAuth flow using the authorized account access available to you. Ask the user to complete any sign-in or approval step you can't perform. Don't open the MCP URL in a browser to sign in: it's a tool endpoint, not a login page.

If a Runpod API key is already available through your client's secret storage, you can configure it as an `Authorization: Bearer` header using the client's supported secret mechanism. Never paste it into chat or a shared configuration file.

MCP authentication is separate from `rp login --agent`. A hosted MCP server doesn't read a local `~/.runpod/config.toml`, and MCP sign-in doesn't configure CLI credentials.

### Step 3: Verify MCP access

List Pods using the Runpod MCP tools. A successful response, including an empty list, verifies access. Don't report the server as connected until an authenticated tool call succeeds, and don't create billable resources to test setup.

The MCP server provides workflow guidance through `list-guides` and `read-guide`, and platform concepts through `lookup-concept` and `search-concepts`. Use those tools when local skills aren't available. You can complete this path without installing skills from a terminal.

## Report the result

Report the path you used and what you verified: CLI access with `rp pod list --json`, or MCP access with its Pod-listing tool. For the CLI path, also report whether the skills are installed and loaded. Don't mark the other path as a missing requirement.

Mark anything awaiting access, user input, or an agent restart as pending, and give the exact next action. Only report account creation or sign-in as successful after authentication completes.

## Feedback

Use `submit_feedback` on the Runpod docs MCP server (`https://docs.runpod.io/mcp`) for documentation feedback. Use `report_feedback` on the Runpod MCP server (`https://mcp.runpod.io/`) for product or MCP-tool feedback. Only call these tools when you have real feedback to report.
